## 1. 背景与目标

当前痛点：

- 歌曲列表封面加载慢；播放页封面慢；多处"重新加载"；
- 频繁切歌、打开播放页、车载页时 UI 卡顿明显；
- 设置页无法查看缓存占用量，清空缓存无二次确认。

目标：

- 同一封面跨页面/跨歌曲命中同一缓存，减少重复下载与 Navidrome 转码；
- 消除播放页大图解码与背景模糊带来的切歌卡顿；
- 设置页可查看各缓存占用量并安全清理。

## 2. 现状盘点（全 App 缓存清单）

## 3. 问题根因分析

### 3.1 加载慢（缓存相关）

1. **URL 高度碎片化**：同一封面按 size 生成不同 URL，全 App 使用数十种尺寸（列表 120、AlbumArtwork 按 `(尺寸×DPR).clamp(200,800)`、播放页 **1200**、车载/首页/迷你条 600、锁屏 size 0 原始分辨率）。每种 size = 独立下载 + 独立磁盘条目 + Navidrome 独立转码。
2. **歌曲封面未归一**：`player_provider.dart:1564` 用 `song.coverArt ?? song.id` 兜底——同一专辑的歌曲 coverArt 为空时生成 N 个不同 URL，专辑封面被重复下载 N 次。
3. **磁盘上限被尺寸稀释**：`maxNrOfCacheObjects 1000` 平摊到多种尺寸后，每种尺寸实际容量仅数百张，大库仍会驱逐重下。

### 3.2 UI 卡顿（缓存无法解决）

| 来源 | 说明 |
|------|------|
| 播放页 1200px 主图解码 | `now_playing_screen.dart:502-521` 每次切歌请求 1200px；即使磁盘命中，主 isolate 解码 1200×1200 位图（5.76MB、数十 ms）仍卡；且该处未设 `memCacheWidth` |
| 背景模糊 `_DynamicBackground` | 每切歌对（大概率 1200px）封面做高斯模糊 |
| 每行 TextPainter 测量 | SongTile 副标题自适应（`song_tile.dart`）与迷你条歌名自适应（`mini_player.dart`）每次 build 做一次文本测宽 |
| Artist tab 重复计算 | `artistSongCounts` 每次 Consumer rebuild 全量遍历 `cachedAllSongs`（`library_screen.dart`） |
| 迷你条毛玻璃 | `BackdropFilter(blur 28)` 常驻每帧渲染（`mini_player.dart:87-88`） |

## 4. 优化方案设计

### 4.1 封面键归一（核心）

```
effectiveCover(song) =
    song.coverArt                        // 服务器返回（Navidrome 通常为专辑封面 id）
    ?? 该专辑的 coverArt（按 albumId 查 cachedAllAlbums）
    ?? song.id（最后兜底，仅确实无封面）
```

- `LibraryProvider` 新增 `effectiveCoverArt(Song)`；✅ 已实施（`library_provider.dart:175`）
- 所有 UI（SongTile 列表、播放页 `_loadArtwork`、player_provider cast/锁屏 URL、车载页）统一使用。
  - ✅ 已用：SongTile 列表（`song_tile.dart:129`）、播放页 `_loadArtwork`（`now_playing_screen.dart:505`）、player_provider `_effectiveCoverId`（cast/锁屏/UPnP，`player_provider.dart:365`）、迷你条（`mini_player.dart:58`，2026-08-03 补齐）、歌曲选项弹窗（`song_tile.dart:410`，2026-08-03 补齐）、车载页（`car_mode_screen.dart:323`，2026-08-03 补齐）、歌词页背景（`synced_lyrics_view.dart:530`，2026-08-03 补齐）

### 4.2 封面尺寸统一（单尺寸 300）

最终方案：全 App 封面请求**统一为单尺寸 300px**（`kCoverArtRequestSize`，`utils/image_cache.dart`），不再分档。同一封面 = 同一 URL = 服务端 1 个缩放缓存条目 + 客户端 1 个磁盘条目 + 1 个内存解码条目，缓存压力最小。

- 播放页主图 1200 → 300（手机屏幕肉眼无差别、解码量降 16 倍）；✅ 已实施（`now_playing_screen.dart:516-523`，主图/缩略图同 300）
- `AlbumArtwork` 去掉 120/300/600 三档 tier，统一 300（URL + `cacheKey` + `memCacheWidth` + 磁盘缩放全一致）；✅ 已实施（`album_artwork.dart`）
- 直连 `getCoverArtUrl` 的页面统一 `size: kCoverArtRequestSize`；✅ 已实施（home_screen、library_screen、car_mode_screen、synced_lyrics_view、library_search_delegate、desktop 侧边栏（经 `library_provider.getCoverArtUrl`）、offline_service 离线封面、AndroidAuto）
- 移除 `getCoverArtUrl(song.coverArt ?? song.id)` 的 song.id 兜底（改走 4.1）；✅ 已实施（统一走 `effectiveCoverArt`）
- 锁屏/cast/UPnP 由系统/接收端渲染，不经 App 图片缓存，未纳入单尺寸（保持各自尺寸）

### 4.3 解码与渐进展示

- 所有 `CachedNetworkImage` 统一 `memCacheWidth`（单尺寸 300）；✅ 已实施（`album_artwork.dart`：`memCacheWidth/memCacheHeight/maxWidthDiskCache` 均 = `kCoverArtRequestSize`）
- 播放页：先渲染 200px 缩略图（列表大概率已缓存），600/300px 大图后台加载完替换；⏸️ 已取消（单尺寸 300 后主图/缩略图为同一 URL，无渐进替换的必要；300px 解码本身已足够小）
- 背景模糊/背景取色用 300px 而非大图，解码成本降 16 倍；✅ 已实施（`_DynamicBackground` 使用 `_cachedImageUrl`=300，`now_playing_screen.dart:568`）
- 新首页取色（2026-08-05）：每日推荐大卡与二级页 hero 渐变取色统一走 `coverCacheManager` + 300 URL（`CachedNetworkImageProvider`，`daily_recommendation_card.dart` / `song_list_screen.dart`），与展示图共享磁盘条目，取色不重复下载
- 补充（2026-08-03）：`AlbumArtwork` 去掉显式 `cacheKey`，**磁盘缓存统一以 URL 为 key**（URL 含固定 size=300 + 稳定 salt），预热/`ImagePreloader`/所有直连点自动共享同一条目；并去掉 `CachedNetworkImage` 上的强制 `ValueKey`，使 `useOldImageOnUrlChange` 生效——切歌时旧封面保持显示直到新图就绪，不再闪占位图
- 更正（2026-08-06）：磁盘 key 由 URL 改为**语义化 key** `coverArt-<serverId>-<id>-<size>`（`utils/image_cache.dart:66-84`，serverId=md5(baseUrl+username)，登录时注册）——换密码不失效、多服务器隔离、可按 id 反查；URL 版 key 构造（`coverArtCacheKeyFromUrl`）供只有 URL 的调用点解析，与 id 版产出相同 key。详见《封面图片缓存优化技术方案》P3

### 4.4 空间换时间

- 全量同步完成后后台**分批预热全部封面**（限速 6 并发 + 批间 sleep 150ms，避免 Navidrome 转码风暴；`downloadFile` 命中缓存自动跳过，增量即只下载缺失）；✅ 已实施（2026-08-03：`_preloadCoverArt` 遍历全部 `_cachedAllAlbums` + 全部歌曲首屏 20 张 + 艺人 20 个，`library_provider.dart`）
- 播放页/车载常用封面按需预热当前专辑 300 档；⏸️ 已由全量预热覆盖（车载页即点即取 300，命中全量预热的同一 URL）

### 4.5 质量换时间

- 播放页 600 → 300（见 4.2），下载/解码减半，肉眼无差别；
- 服务端可另配 Navidrome 封面转码缓存预热脚本（一次性 curl 全库 120px），首访命中服务端缓存。

## 8. 转码播放缓存分析（待讨论）

> 状态：已完成源码排查与官方确认，方案待定，未实施。

### 8.1 现状（3 处一致的策略）

| 位置 | 场景 | 行为 |
|------|------|------|
| `_buildAudioSourceForSong`（gapless 队列，`player_provider.dart:2788-2827`） | 转码开 → 裸流不缓存；关 → `LockCachingAudioSource` 缓存到 `<tmp>/musly_stream_<song.id>.tmp` | L2812-2814 / L2817-2826 |
| `playSong`（单曲路径，`player_provider.dart:1828-1881`） | 同上 | L1855-1862 / L1864-1876 |
| `_prepareCurrentSong`（恢复路径，`player_provider.dart:2840-2901`） | 同上 | L2871-2877 / L2878-2892 |

本地/离线文件走 `setUrl`，无需缓存。

> 2026-08-05 补充：流缓存清理已落地——`StreamingCacheCleaner`（`services/streaming_cache_cleaner.dart:9-62`）在每曲播放结束后按 mtime 清 `musly_stream_*.tmp` 至 ≤2GB（上限常量 `_defaultMaxBytes`），并打点 `cachePrune` 事件。缓存文件位于 `getTemporaryDirectory()`，系统可清、跨会话不保证命中（见 §8.8 与 Ultrasonic 对照）。

### 8.2 issue #170 的根因

`LockCachingAudioSource`（just_audio）通过本地 HTTP 代理播放缓存文件：

- seek 到**已缓冲区域** → 本地直接跳转，正常；
- seek 到**未缓冲区域** → 代理向源 URL 发 HTTP Range 请求补数据；
- **源不支持 Range（返回全量 200）→ 代理退化为从头重启下载**（当年选裸流的原因：至少 ExoPlayer 能保缓冲区内 seek）。

### 8.3 Navidrome 官方确认（GitHub discussion #5712，维护者 deluan）

> - 非转码流：完整 HTTP Range 支持；
> - 转码流：**服务端转码缓存命中时支持 Range；全新转码（缓存未命中）时不支持**；
> - Navidrome 有服务端转码缓存（`TranscodingCacheSize`），转码产物按（歌曲, 参数）缓存。

### 8.4 "首次转码"场景定义

指 **某首歌 + 某组转码参数在 Navidrome 服务端第一次生成转码产物**（服务端缓存未命中），与设置开关何时打开无关。影响：

| 场景 | seek 行为 |
|------|----------|
| 首次转码（服务端缓存未命中，无 Range） | 只能拖已缓冲区域，拖超缓冲可能重启 |
| 重播 / 服务端转码缓存命中（有 Range） | 任意位置可拖 |
| 设置中途开关转码 | 从下一首歌生效（当前歌保持原流） |

### 8.5 现状问题

转码场景（远程 + 转码是重要使用场景）**完全不缓存** → 重播同一首歌重新下载，浪费网络；且"首次转码"的 seek 限制其实一直存在（裸 ExoPlayer 在无 Range 流上同样拖不过缓冲区）。

### 8.6 候选方案

- **方案 A（推荐先试，~15 行）**：3 处删除 `if (_transcodingService.enabled)` 裸流分支，转码流统一走 `LockCachingAudioSource`。收益：转码流落本地缓存、重播免下载、绝大多数场景（服务端缓存命中后）可任意拖；代价：首次转码 + seek 超缓冲仍受限（罕见组合）。
- **方案 B（进阶，~200 行）**：自定义 `StreamAudioSource`，seek 超出缓存时用 Subsonic `stream?timeOffset=<秒>` 重新请求（服务端 seek 转码器输入，不依赖 HTTP Range），彻底实现"转码 + 缓存 + 任意位置拖动"。

### 8.7 相关发现

设置页"音乐缓存"开关（`CacheSettingsService`）目前是**死开关**——只有设置页读写，无任何业务代码消费。其命名/描述（"本地保存歌曲元数据"）疑似本意是控制播放流缓存，可考虑在方案 A/B 实施时让开关真正控制"是否缓存播放流（含转码）"。

### 8.8 Ultrasonic 客户端对照（2026-08-05）

> 参考：`docs/ultrasonic客户端技术文档.md`（源码 commit `1d50ee38`）。本小节记录 Luobo 现状与 Ultrasonic 实现的差异，供方案 A/B 决策参考。

#### 8.8.1 封面缓存对照

| 维度 | Luobo | Ultrasonic |
|------|-------|-----------|
| 请求尺寸 | 统一单尺寸 300（`kCoverArtRequestSize`，`utils/image_cache.dart:10`） | 多尺寸按 UI 传参（`ImageLoader.kt:144` `resolveSize(size, large)`），无全局统一档 |
| 键归一 | `effectiveCoverArt`：coverArt → 专辑封面 → song.id（`library_provider.dart:175-183`）；磁盘 key = `coverArt-<serverId>-<id>-<size>`（2026-08-06 起语义化，见《封面图片缓存优化技术方案》P3） | key = `getAlbumArtKey(entry, large)`（`ImageLoader.kt:125`），md5 命名；不同页面不同 size → 不同缓存条目，无跨页面归一 |
| 磁盘缓存 | flutter_cache_manager：60 天 stale、**10000 张**（2026-08-06 起，基本不驱逐）+ `CoverCacheCleaner` 512MB 字节守护；解码 `memCacheWidth=300` | 自管 `artwork/` 目录**双档**：`<md5>.jpeg`（大）/ `<md5>.jpeg-small`（小）+ 专辑目录 `folder.jpeg`（`FileUtil.kt:49-50,171`） |
| 大图降采样 | 无（单尺寸方案已取消大图） | 有：小档 miss 查大档（`CoverArtFetcher.kt:75-82`），磁盘解码 `inSampleSize` 按目标 size 降采样（`CoverArtFetcher.kt:103-129`），大图文件被多尺寸复用 |
| 内存缓存 | Flutter `ImageCache` 300 张 / 150MB | Coil3，25% 可用 heap（`UApp.kt:103-113`） |
| 主动缓存 | 首请求即写盘；全量预热 6 并发 + 150ms 批间（`library_provider.dart:687-695`） | `downloadCoverArt` 恒定拉大尺寸（`ImageLoader.kt:193-219`）；下载/固定歌曲时顺带缓存（`DownloadTask.cacheMetadataAndArtwork`）；无全量预热 |

结论：Luobo 单尺寸 + URL 归一（服务端 1 个转码条目 + 客户端 1 个磁盘条目 + 1 个内存条目）已优于 Ultrasonic 的多尺寸方案；Ultrasonic 的"大图文件 + 降采样复用"仅在需要桌面端/通知栏高清大图时有参考价值。

#### 8.8.2 在线听歌缓存对照（转码 vs 非转码）

| 差异点 | Luobo | Ultrasonic |
|--------|-------|-----------|
| 写入时机 | 边播边写（当前曲，`LockCachingAudioSource`） | 播放只读缓存（`CachedDataSource`），**写入统一由下载引擎**：`cacheNextSongs()` 预加载后续 N 首（高优先级，`PlaybackService.kt:346-363`） |
| 转码流 | **不缓存**（保 seek 优先，issue #170） | **照常参与预加载缓存**（省重播流量优先）；转码首播（服务端转码缓存未命中）无 Range，用"读超时随 offset 放大"兜底（`RangeHeaderInterceptor.kt`） |
| 文件体系 | 播放 tmp 缓存与离线下载**两套** | 播放缓存 / 固定 / 离线**一套**：`<artist>/<album>/NN-title.complete.ext`（可驱逐）/ `.pinned`（固定，`FileUtil.kt:83-90`），rename 互转 |
| 持久性 | `getTemporaryDirectory()`，系统可清、跨会话不保证命中；`StreamingCacheCleaner` 清到 ≤2GB | 持久文件，可驱逐、可离线复用；`CacheCleaner` 按容量清 complete |
| 缓存键 | `musly_stream_<song.id.hashCode>.tmp`（理论碰撞风险） | 规范化文件名（artist/album/title），无碰撞 |

#### 8.8.3 对方案 A/B 的参考

1. Ultrasonic 转码流也能缓存，靠的是**预下载到 `.complete` 再播**（`cacheNextSongs`），而非播放中代理缓存——其"首次转码 + seek 超缓冲受限"与 Luobo 裸流方案本质相同，接受"首播受限、重播完美"即可套用；
2. 若实施方案 A（转码也走 `LockCachingAudioSource`），缓存文件应放到 App 文档目录（可跨会话复用）+ 保留 2GB 清理逻辑，对齐 Ultrasonic `CacheCleaner`；
3. `song.id.hashCode` 建议改稳定键（歌曲 id 原文，且含 maxBitRate/format，避免转码参数变化串档）；
4. 设置页"音乐缓存"死开关（§8.7）可在方案 A 实施时真正接线为"是否缓存播放流（含转码）"。

## 9. 箭头音乐（Amcfy）封面缓存对照（2026-10-20）

> 用户反馈「Amcfy 每次冷启图片都很快」。本节基于 Amcfy Music 1.2.15 APK 的静态分析（`libapp.so` AOT 字符串、`NOTICES.Z`、`classes.dex`），只做机制对照，不运行其 App。

### 9.1 APK 实证：它用了什么

- **`flutter_cache_manager`**：AOT 字符串里有完整的 `cacheObject` 表结构与 SQL：
  ```sql
  create table cacheObject (
    key text primary key,
    relativePath text,
    eTag text,
    validTill integer,
    touched integer
  )
  ```
  这是 `flutter_cache_manager` 的标准元数据表（key / 文件相对路径 / ETag / 过期时间 / 最近访问）。
- **自定义 `CoverCache` 包装层**：`/.cover_cache_v2`、`CoverCache.get`、`CoverCache._download`、`customCacheDirectory`、`getCacheDir`、`clearCoverCache`、`Download skipped ... cache_directory_not_ready / cache_directory_resolution_failed`。
- **`octo_image`**：NOTICES 里命中 `octo_image`，没有 `cached_network_image`；说明图片 widget 走 `octo_image`（占位/淡入），底层仍是 `flutter_cache_manager`。
- **服务端缩略图**：AOT 字符串里有 `/Images/Primary?maxWidth=100`、`/Images/Primary?fillHeight=`、`/api/proxy-image`、`/api/v1/cover?path=`、`/rest/getCoverArt`、`cover?ts=`、`image?ts=`，以及 `imageTagJson` / `PrimaryImageTag` / `AlbumPrimaryImageTag`。
- **缓存设置**：设置页有 `Cover Cache`、`Cache limit`、`Clear cached files`、`/settings/cache/clear`，说明封面缓存有独立容量上限与清理入口。
- **默认目录**：`/libCachedImageData`（`flutter_cache_manager` 默认文件目录）+ `/.cover_cache_v2`（自定义缓存根目录）；同时出现 `getApplicationSupportDirectory` 与 `getTemporaryDirectory`，说明它对「持久目录 vs 临时目录」做了显式选择。

### 9.2 冷启动快的原因（推断，按贡献排序）

1. **磁盘缓存跨会话**：`cacheObject` + 文件目录持久化，冷启直接命中，不重新下载。
2. **列表用小图**：`maxWidth=100` 的缩略图，下载字节和解码像素都远小于 300px；首屏渲染快，感知上就是「秒出」。
3. **ETag / validTill / imageTag**：缓存键带服务端图片版本，命中时不需要重新校验；`?ts=` 只在图片真正变化时变。
4. **`octo_image` 占位 + 淡入**：即使磁盘未命中，也先画占位，不阻塞首帧；命中时几乎无闪烁。
5. **不依赖全库预热**：首屏只加载可见项，冷启动不被「全量封面预热」拖住（AOT 里没有发现全量预热的证据）。
6. **持久目录优先**：`getApplicationSupportDirectory` 的存在说明封面不完全是临时缓存，系统清理后仍可能保留。

### 9.3 与 Luobo 现状对比

| 维度 | Luobo | Amcfy |
|---|---|---|
| 库 | `cached_network_image` + `flutter_cache_manager` | `flutter_cache_manager` + `octo_image` + 自定义 `CoverCache` |
| 磁盘键 | 语义化 `coverArt-<serverId>-<id>-<size>` | URL + `imageTag` / `PrimaryImageTag`（必要时 `?ts=`） |
| 尺寸 | 全 App 单尺寸 300（`kCoverArtRequestSize`） | 多档：列表约 100，详情更大；服务端缩放 |
| 磁盘策略 | 60 天 stale、10000 张、`CoverCacheCleaner` 512MB 字节守护 | `cacheObject.validTill/touched` + 独立容量设置 |
| 内存 | Flutter `ImageCache` 300 张 / 150MB | Flutter `ImageCache` + `octo_image` |
| 预热 | 全库分批预热（6 并发 + 150ms 批间） | 未发现全库预热；更像首屏/可见项按需加载 |
| 目录 | `flutter_cache_manager` 默认（注释见 `cover_cache_cleaner.dart`） | `/.cover_cache_v2` + `libCachedImageData`，显式选择持久目录 |

**结论**：Luobo 的缓存体系并不落后——语义化 key、512MB 字节守护、全量预热都比 Amcfy 更激进。Amcfy 冷启更快的最大差异不是「缓存库」，而是**列表用小图 + 首屏按需加载 + 占位淡入**；Luobo 的「单尺寸 300 + 全量预热」是用首屏速度换缓存命中率。

### 9.4 对齐建议（先测量，不盲目换库）

1. **A/B 两档尺寸**：列表/网格用 100–150px，详情/播放页保持 300；`memCacheWidth` 同步。用冷启动首屏「第一张图出现时间」和「首屏下载字节数」做对照，不要只凭观感。
2. **首屏可见项预取**：在首帧前只预取首屏可见的 10–20 张，不要等全库预热；全库预热保留在后台。
3. **缓存键加图片版本**：如果道理鱼返回 `imageTag` / `PrimaryImageTag`，把它并入 key（或作为 ETag），避免封面更新后仍命中旧图；没有版本字段就保持现有语义 key。
4. **持久目录**：确认 `coverCacheManager` 的文件目录在应用支持目录而非纯临时目录；如果系统清理后冷启大量 miss，再迁移。
5. **占位与淡入**：`CachedNetworkImage` 已有 placeholder；可评估 `octo_image` 的 fade-in 体验，但收益主要是感知，不是速度。
6. **不要替换 `flutter_cache_manager`**：Amcfy 的自定义 `CoverCache` 没有证据表明比 Luobo 现有方案更快；它的优势在尺寸策略和首屏加载时机。

### 9.5 最小验证清单

- 冷启动首屏：记录「首张封面出现时间」「首屏请求数/字节数」「磁盘命中率」；
- 列表滚动：记录「新出现封面的平均加载时间」；
- 切到详情/播放页：确认 300px 图已命中，不重复下载；
- 清理缓存后冷启：确认持久目录策略是否符合预期；
- 对比 A（现状单尺寸 300）与 B（列表 120 / 详情 300）两组数据，再决定是否改。

> 一句话：Amcfy 的快主要来自「小图 + 磁盘命中 + 占位」，不是某个神秘缓存库；Luobo 已有同等基础设施，优先做尺寸分层与首屏预取，而不是重写缓存层。
