# Luobo 音频打断（Audio Focus / Interruption）处理技术方案

> 状态：**方案 B 已实施（2026-10-08）** —— `flutter analyze` 零新增 error/warning、`flutter test` **253 通过 / 5 跳过**（含新增 `test/services/audio_interruption_policy_test.dart` 10 条）；**待真机验收**（§6.2 五场景）。实施偏差与新增发现见 §9。
> 范围：Android 端「播放中被其他 App / 电话 / 导航播报打断」时的**暂停与恢复**行为；**不含** Cast/UPnP 远程播放的会话管理，**不含** iOS（iOS 现状已正确，见 §2.3，本次不动）
> 依据：Luobo master（v1.1.18）源码实证 + 依赖库源码（`just_audio 0.9.46` / `audio_session 0.1.25`）+ MusicFree 0.6.2（RNTP 4.1.1 + KotlinAudio v2.1.0）对照
> 触发问题：用户反馈「音乐被别的程序打断时 Luobo 不会暂停，一直在播放但没声音了，每次都需要手动暂停再播放才会有声音」

---

## 1. 背景与现象

| 现象 | 用户描述 | 本文结论 |
|---|---|---|
| 打断后不暂停 | 「luobo 不会暂停，而是一直在播放」 | **缺陷**：播放器确实没停 —— 恢复播放被 `just_audio` 库内部接管，UI 状态随库同步成「播放中」（§3.1） |
| 在播但无声 | 「但是没有声音了」 | **缺陷**：播放器音量被本 App 的暂停路径压到 0，而恢复路径不经过本 App，音量再也没被拉回来（§3.1） |
| 必须手动暂停再播放 | 「每次都需要手动暂停再播放才会有声音」 | **同一根因的必然结果**：手动 `play()` 会走 `_fadeIn()`，那是全项目唯一恢复音量的地方（§3.1） |

> 一句话：**这不是「没处理打断」，而是「暂停时把音量归零 + 恢复播放被库抢走」，两件事错配导致的静音失联。**

对照结论（用户提到「别人都是暂停」）：MusicFree 的暂停与音量**完全解耦**，且恢复播放由它自己的 JS 控制层执行，因此结构上不可能出现「在播但无声」（§3.5）。**方案 B 的目标就是把 Luobo 的 Android 侧对齐到这个结构。**

## 2. 现状链路（代码实证）

### 2.1 Android 上音频焦点由谁管

| 层 | 实现 | 位置 |
|---|---|---|
| ExoPlayer | **不管焦点** —— just_audio 显式传 `handleAudioFocus=false` | `just_audio-0.9.46/android/.../AudioPlayer.java:329` / `:356` / `:816` |
| 音频焦点（Android） | `audio_session` 独占管理 | `audio_session-0.1.25/android/.../AndroidAudioManager.java:300-337` |
| 焦点事件 → Dart | `interruptionEventStream` | `audio_session-0.1.25/lib/src/core.dart:254-285` |
| 自研原生插件 | **空转**：`_handleAudioFocus=false` → 原生 `requestAudioFocus()` 直接 `return true`，**不注册焦点监听** | `lib/services/android_system_service.dart:41-42` + `android/.../AndroidSystemPlugin.kt:203` |
| 打断处理（App 层） | 双重订阅同一个流：① `just_audio` 库内 ② Luobo 自己的监听 | `just_audio.dart:302-348` + `player_provider.dart:1582-1610` |

> 关键事实：**Android 上没有第三套焦点逻辑**，`_handleAudioFocus=false`（提交 `9598344`，2026-05-09「解决焦点冲突导致无法起播」）之后，自研插件里那套 `audioFocusListener` 是死代码。

### 2.2 打断发生时的完整时序（当前实现）

以「瞬时打断」（电话 / 导航播报 / 语音消息）为例：

```
另一个 App 请求 AUDIOFOCUS_GAIN_TRANSIENT
 └─ audio_session 原生 onAudioFocusChange          AndroidAudioManager.java:306-309
     └─ Dart 发射 begin=true, type=pause           core.dart:269-273
         ├─ just_audio 库内监听（订阅在前）          just_audio.dart:320-327
         │   └─ playing → pause() + _playInterrupted = true
         └─ Luobo 自己的监听                         player_provider.dart:1593-1597
             └─ pause() → _fadeOut() → 音量→0 → _audioPlayer.pause()
                 （音量恢复只由 _fadeIn() 负责，唯一调用点 :2633，在 play() 里）

打断结束 AUDIOFOCUS_GAIN
 └─ Dart 发射 begin=false, type=pause               core.dart:256-263
     ├─ just_audio 库内监听                         just_audio.dart:337-339
     │   └─ if (_playInterrupted) play()   ← 库自己恢复播放，不经过本 App
     └─ Luobo 自己的监听                             player_provider.dart:1599-1608
         └─ pause/unknown 分支：什么都不做（注释 "Optionally resume after interruption ends"）
              ⇒ 播放器在播（位置照走） + 音量仍为 0 ⇒ 完全无声
```

### 2.3 iOS 为什么没有这个问题（本次不动）

iOS 侧原生在打断结束时会把事件发回 Dart：

```swift
case .ended:
    if options.contains(.shouldResume) { sendEvent("audioFocusGain", data: nil) }
```
—— `ios/Runner/iOSSystemPlugin.swift:242-247`

Dart 收到后就是「把音量恢复到设定值」：

```dart
_androidSystemService.onAudioFocusGain = () {
  if (isRemotePlayback) return;
  _smoothVolumeChange(_volume);      // player_provider.dart:485-488
};
```

所以 iOS 上打断结束 = 暂停 + **音量已恢复**，点播放立刻有声。同一套 Dart 回调在 Android 上是死代码（§3.4）。

## 3. 根因

### 3.1 主因：暂停把音量归零，而恢复播放被库抢走

**① 暂停 = 音量归零 + pause（两步）**

`player_provider.dart:2723-2760`
```dart
} else {
  await _fadeOut(onComplete: () async {
    await _audioPlayer.pause();
  });
```

`_fadeOut()`（`:2821-2851`）**无论是否开启淡入淡出都会把音量压到 0**：

- 关闭淡入淡出（默认 `fadeEnabled=false`）→ `await _audioPlayer.setVolume(0.0)`（`:2825`）
- 开启 → 20 步渐变到 0（`:2839-2849`）

**② 恢复音量的路径只有一条**：`_fadeIn()`（`:2791-2819`），全仓唯一调用点是 `play()` 里的 `:2633`（`grep _fadeIn` 仅此一处）。

**③ 但打断结束后的「恢复播放」不是 Luobo 做的**：`AudioPlayer` 是零参数构造（`lib/services/audio_handler.dart:25`），`handleInterruptions` 默认 `true`，`just_audio` 自己订阅了同一个流并在结束时 `play()`（`just_audio.dart:337-339`）。

**④ 于是状态就是「在播 + 音量 0」**，而 UI 会显示播放中：

```dart
_isPlaying = state.playing;      // player_provider.dart:1366
```

> 结论：**暂停与恢复被拆到了两层**。暂停时本 App 负责「音量归零」，恢复时库负责「继续播放」，中间那步「音量拉回来」没人做。方案 B 的着力点就是**把恢复播放也收回 App 层**，让 `play() → _fadeIn()` 这条唯一正确的路径重新成为唯一入口。

### 3.2 三类打断的表现矩阵

按 `audio_session-0.1.25/lib/src/core.dart:254-285` 的映射：

| 焦点事件 | audio_session 事件 | Luobo 现状 | 是否踩中本缺陷 |
|---|---|---|---|
| `AUDIOFOCUS_LOSS_TRANSIENT`（电话 / 导航 / 语音） | begin=true, **type=pause**；结束 begin=false, type=pause | 暂停；库自动恢复播放 | ✅ **踩中**（听感上"没暂停过、只是没声音了"） |
| `AUDIOFOCUS_LOSS`（别的音乐/视频 App 抢焦点） | begin=true, **type=unknown**；**永远不会来结束事件** —— 原生在收到 LOSS 时先 `abandonAudioFocus()` 注销监听（`AndroidAudioManager.java:307`） | 暂停，不自动恢复 | ❌ 不踩中（表现为"正常暂停"，手动播放有声） |
| `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK` | begin=true, type=duck（`music()` 配置 `willPauseWhenDucked=false`） | 只降到 0.3（`:1591`），结束回到 `_volume`（`:1602`） | ❌ 不踩中（有声，只是变小） |

> 补充：Android 侧 `type=unknown` **只会**出现在 `AUDIOFOCUS_LOSS`（永久抢焦点），结束事件只可能是 `duck` 或 `pause`（`core.dart:256-263`）。这条事实是方案 B 里「`unknown` 不置恢复标记」的依据。

### 3.3 自愈机制的盲区

`_checkSilentPlayback()`（`:2654-2721`）的无声判定：

```dart
final stuck = !_audioPlayer.playing ||
    _audioPlayer.processingState == ProcessingState.idle ||
    (_audioPlayer.processingState == ProcessingState.ready && advancedMs < 500);   // :2686-2690
```

- 只抓「没在播 / 源失效 / 位置停滞」；`silentLikely` 指纹甚至**要求 `volume > 0.01`**（`:2674`）
- **「在播 + 位置前进 + 音量 0」是它的盲区**
- 更关键：它只在 `play()` 里启动（`:2636`）。而本缺陷的恢复播放由**库**发起、**不经过 `play()`** ⇒ 检测器根本不会启动，自愈无从谈起

> 方案 B 完成后，恢复播放会重新走 `play()` ⇒ 该检测器随之被激活，兜底（§4.4）才有意义。

### 3.4 死代码：本该兜底的 `onAudioFocusGain` 在 Android 永不触发

`:485-488` 写了「焦点恢复 → 恢复音量」，但 `_handleAudioFocus=false` 让原生侧压根没注册焦点监听（`AndroidSystemPlugin.kt:203`），这几个回调在 Android 上是死代码 —— **兜底能力写好了，但没接上电**。

> 方案 B **不复用**这套回调（它依赖自研原生插件重新抢焦点，会与 `audio_session` 冲突，见 §8）。Android 的打断处理统一收敛到 Dart 侧的 `interruptionEventStream`。

### 3.5 与 MusicFree 的对照

| 维度 | MusicFree（RNTP 4.1.1 + KotlinAudio v2.1.0） | Luobo 现状 | 方案 B 后 |
|---|---|---|---|
| 暂停是否动音量 | **不动**。`pause()` 只有 `exoPlayer.pause()`（`BaseAudioPlayer.kt:398-400`） | **动**：音量压到 0（`_fadeOut`，`:2825`） | 不动（保留 `_fadeOut`，但恢复必走 `play()`） |
| 打断决策在哪一层 | **JS service 独占**（`src/service/index.ts:19-55`），原生只发事件 | 两层叠加：库内 + App 层 | **App 层独占**（关掉库内处理） |
| 恢复播放由谁发起 | **JS 自己** `TrackPlayer.play()`，配合 `resumeState` 判断打断前是否在播 | **库内部**（`just_audio.dart:337-339`），绕过 App 层 | **App 自己** `play()`，配合 `_wasPlayingBeforeInterruption` |
| 能否出现「在播但无声」 | **结构上不可能** | 可复现（§3.1） | 结构上不可能 |

> 差异的本质不是"谁更聪明"，而是**「暂停/恢复」是否由同一层负责、以及恢复是否走 App 自己的控制层**。方案 B 把 Luobo 对齐到 MusicFree 的两条。

## 4. 方案

### 4.1 方案 B（**采用**）：Android 收回打断处理权

思路：**让 App 层成为 Android 打断的唯一决策者** —— 关掉 `just_audio` 的库内处理，暂停与恢复都由 Luobo 自己发起，恢复走 `play() → _fadeIn()`，音量自然被拉回。

#### 步骤 1：关掉 Android 侧的库内打断处理

`lib/services/audio_handler.dart:25`
```dart
final AudioPlayer _player = AudioPlayer(
  // Android：打断处理由 App 层独占（本文件 §4.1）。
  // iOS：保持库内处理 —— _configureAudioSession() 是 Android-only
  //（player_provider.dart:1561），关掉会让 iOS 彻底失去打断处理。
  handleInterruptions: defaultTargetPlatform != TargetPlatform.android,
);
```

- 用 `defaultTargetPlatform`（而非 `Platform.isAndroid`）：便于单测用 `debugDefaultTargetPlatformOverride` 覆盖，与项目既有约定一致
- 该参数只影响 **Dart 侧**对 `interruptionEventStream` 的订阅（`just_audio.dart:302-348`）；ExoPlayer 本来就不管焦点（§2.1），**不涉及原生改动**
- 副作用：同时移除库内的 `becomingNoisyEventStream` 订阅（`just_audio.dart:304-307`）与 `usage=game` 的 duck 处理。前者 Luobo 自己有（`:1613-1621`），后者与本项目 `usage=music` 无关 —— **均无影响**

#### 步骤 2：App 层接管（新增标记 + 统一处理入口）

```dart
/// 打断前是否在播放（等价 MusicFree 的 `resumeState`）。
/// 只在 type==pause（瞬时打断）时置位：unknown（永久 LOSS）不会再有结束
/// 事件，置位只会让后续无关的结束事件误触发恢复播放。
bool _wasPlayingBeforeInterruption = false;
```

`_configureAudioSession()` 的监听体收敛为一行调用（保留原诊断埋点）：

```dart
session.interruptionEventStream.listen((event) {
  DiagnosticsService.instance.record(
    EventType.audioInterruption,
    LogLevel.info,
    {'begin': event.begin, 'type': event.type.name},
  );
  unawaited(_handleInterruptionEvent(event));
});
```

新增唯一处理入口（`audio_session` 类型已 import，`:7`）：

```dart
/// Android 打断处理的唯一入口（方案 B：库内处理已关闭）。
/// 决策表见 docs/音频打断处理技术方案.md §4.1。
Future<void> _handleInterruptionEvent(AudioInterruptionEvent event) async {
  // 远程播放：本地播放器被有意暂停，不干预（沿用既有守卫语义）
  if (isRemotePlayback) return;

  if (event.begin) {
    switch (event.type) {
      case AudioInterruptionType.duck:
        _audioPlayer.setVolume(0.3);          // 保持既有 duck 语义，不顺手改
        break;
      case AudioInterruptionType.pause:       // 瞬时打断：可恢复
        _wasPlayingBeforeInterruption = _audioPlayer.playing;
        await pause();
        break;
      case AudioInterruptionType.unknown:     // 永久抢焦点：不恢复
        _wasPlayingBeforeInterruption = false;
        await pause();
        break;
    }
  } else {
    switch (event.type) {
      case AudioInterruptionType.duck:
        _audioPlayer.setVolume(_volume);
        break;
      case AudioInterruptionType.pause:       // 打断结束：走 App 的 play()
        final shouldResume = _wasPlayingBeforeInterruption;
        _wasPlayingBeforeInterruption = false;
        if (shouldResume) await play();       // → _fadeIn() 恢复音量
        break;
      case AudioInterruptionType.unknown:     // Android 不会走到，防御性清标记
        _wasPlayingBeforeInterruption = false;
        break;
    }
  }
}
```

**事件决策表**（与 §3.2 一一对应）：

| 事件 | 动作 | 标记 | 理由 |
|---|---|---|---|
| begin + duck | 音量 → 0.3 | 不动 | 既有行为，有声不静音 |
| begin + pause（在播） | `pause()` | `true` | 瞬时打断，结束后应恢复 |
| begin + pause（已暂停） | `pause()`（幂等） | `false` | 打断前没在播，结束后不得自动播 |
| begin + unknown | `pause()` | `false` | 永久 LOSS，不会再有结束事件（§3.2） |
| end + duck | 音量 → `_volume` | 不动 | 既有行为 |
| end + pause | `play()`（若标记为真） | 清 `false` | **关键修复点**：恢复走 App 层，`_fadeIn()` 拉回音量 |
| end + unknown | 无动作 | 清 `false` | 防御性 |

#### 步骤 3：标记的清理点（防残留误恢复）

| 位置 | 说明 |
|---|---|
| `play()` 入口 | 用户主动播放意图（handler 在调用 `play()` **之前**已清，故不冲突） |
| `playSong()` / `_startPlayback()` | 切歌不经过 `play()`（`:2019` / `:2036` / `:2057` / `:2097`），必须显式清 |
| `stop()` | 用户主动停止 |
| `seek()` | 用户主动干预 |
| `skipNext()` / `skipPrevious()` | 用户主动切歌 |
| Cast / UPnP 连接分支 | 切远端后本地播放器不参与 |

> ⚠️ **`pause()` 默认清标记，打断路径显式保留**（2026-10-08 code-review R1 修订，原表述为「`pause()` 内不得清标记」）：打断是「先置位、再 `await pause()`」，若 `pause()` 无条件清标记，标记会被自己清掉、恢复逻辑永久失效；但反过来「一律不清」也有害 —— 打断期间用户手动暂停（媒体会话暂停按钮、拔耳机 `becomingNoisy`，都不经 `_isPlaying` 守卫）后，`end + pause` 仍会把音乐自动拉起来。
> 实现口径：`pause({bool skipFade = false, bool keepInterruptionResume = false})`，**默认清标记**（用户主动暂停即作废自动恢复意图）；仅打断路径传 `keepInterruptionResume: true` 显式保留。

#### 步骤 4（推荐）：打断路径跳过淡出尾巴

`pause()` 目前会先 `_fadeOut` 再真正暂停；关闭淡入淡出时是瞬时的，**开启时最多延迟 `fadeDurationMs`（默认 300ms）才静音**。库内处理关闭后，这 300ms 里没有任何人暂停播放器。建议：

```dart
Future<void> pause({bool skipFade = false}) async { ... }
// 打断路径：await pause(skipFade: true);
```

`skipFade: true` 时直接 `setVolume(0.0)` + `_audioPlayer.pause()`（即复用 `_fadeOut` 关闭淡入淡出时的分支），保证打断即静音。约 5 行。

### 4.2 方案 A（**降级为回滚备选**）：只补回「打断结束恢复音量」

保留库内处理，仅在打断结束分支补一行：

```dart
case AudioInterruptionType.pause:
case AudioInterruptionType.unknown:
  if (isRemotePlayback) return;
  _smoothVolumeChange(_volume);   // 与 iOS 的 onAudioFocusGain 对齐（:485-488）
  break;
```

- **1 文件 / ~4 行**，直接命中症状，结构风险最低
- 但**保留了「两层负责暂停/恢复」的结构**（§3.1 的根因未消除），且 `_checkSilentPlayback` 依旧不会被激活
- 用途：若方案 B 真机回归出现不可接受的回归，可整体回退到 A 作为止血

### 4.3 方案 C（**不采用**）：照搬 MusicFree 的可配置项

MusicFree 多两个设置项：「允许与其他应用同时播放」(`basic.notInterrupt`)、「打断时降低音量 / 暂停」(`basic.tempRemoteDuck` + 音量档位，见 `src/entry/bootstrap/bootstrap.ts:166-191` 与 `src/service/index.ts:19-55`）。

Luobo 目前是硬编码（pause + duck 0.3）。要做这两个开关，成本主要在**设置页 + 持久化 + 30 个语言文件**（`lib/l10n/app_localizations_*.dart` 共 30 个），约 150~250 行，且与本次缺陷无因果关系 —— 除非确实要这个可配置性，否则不立项。

### 4.4 兜底（建议随 B 一起做）：补 `_checkSilentPlayback` 的音量盲区

```dart
// 在现有 stuck 判定上补一条：在播 + 位置前进 + 音量≈0
final silentByVolume = _audioPlayer.playing &&
    _audioPlayer.processingState == ProcessingState.ready &&
    advancedMs >= 500 &&
    _audioPlayer.volume < 0.01;
final stuck = /* 现有三条 */ || silentByVolume;
```

- 恢复动作：**直接 `_audioPlayer.setVolume(_volume)`**（轻量、无副作用），事件里记 `recovery: 'restoreVolume'`
- **不要复用现有的 reprepare 恢复分支**：那条路径（`:2703-2714`）只 `_prepareCurrentSong()` + `_startPlayback()`，**不恢复音量**，修不了这个场景
- 定位：方案 B 已从结构上消除该状态，这里是**回归防线**（覆盖未来未知路径）

### 4.5 方案对比

| 方案 | 做法 | 改动量 | 结论 |
|---|---|---|---|
| **B. 收回打断处理权** | 关库内处理 + App 自管 pause/resume + 标记清理 | **2 文件 / ~50 行**（含 `skipFade` 与抽方法） | ⭐ **采用**：消除「两层负责」的结构根因，对齐 MusicFree；代价是需真机回归 4 类场景 |

## 7. 风险与回滚

| 风险 | 应对 |
|---|---|
| **iOS 跟着失去打断处理** | 必须按平台传参（步骤 1）；iOS 保持 `handleInterruptions: true`，且 `_configureAudioSession()` 本来就不在 iOS 执行（`:1561`）。回归清单里加一条 iOS 电话打断用例 |
| **`pause()` 与标记的交互**（2026-10-08 code-review R1 修订） | 原设计「`pause()` 一律不清标记」与 §6.2 场景 5（打断期间手动暂停后不得自动播放）冲突。改为：`pause()` **默认清**标记，打断路径传 `keepInterruptionResume: true` 显式保留（§4.1 步骤 3） |
| **标记残留 → 误恢复播放** | 只在 `type==pause` 置位；`unknown` 置 false；用户操作/切远端一律清位；用例 9 覆盖 |
| 打断瞬间的淡出尾巴（fade 开启时最长 300ms 未静音） | 步骤 4 的 `skipFade: true`（推荐一起做） |
| duck 语义被顺手改动导致回归 | 步骤 2 里 duck 分支**原样保留** `setVolume(0.3)` / `setVolume(_volume)`，不改成 `_smoothVolumeChange` |
| 库内处理关闭后，若 App 层漏了某类事件 → 无人暂停 | 决策表按 §3.2 三类事件穷举；用例 1~8 覆盖全部分支；真机场景 2、3 专门验证非 pause 路径 |
| `_smoothVolumeChange()` 内部 `_stopFade()` 取消进行中的淡入淡出 | 仅 §4.2（方案 A）路径涉及；B 不引入该调用 |
| 真机回归面比 A 大 | 方案 A 保留为整体回滚目标（§4.2），单 commit 可退 |

**回滚**：改动集中在 2 个 Dart 文件，无持久化 / 数据结构 / 原生改动。若真机回归不通过，按 §4.2 回退到方案 A（改 1 处、约 4 行）。

### 9.1 实施偏差与新增发现

| # | 项 | 说明 |
|---|---|---|
| 1 | **决策与执行分离**（原计划的「私有 `_handleInterruptionEvent`」不可单测） | Dart 的私有成员是**库级**可见，`test/` 下的用例无法调用 `player_provider.dart` 的私有方法 ⇒ §6.1 承诺的 9 条用例无法落地。改为把决策表抽成纯函数 `decideInterruption()`（新文件 `lib/services/audio_interruption_policy.dart`），`_handleInterruptionEvent()` 只保留一个 switch 执行副作用。收益：单测零 stub、零播放器依赖；代价：多一个文件 |
| 2 | **`skipFade` 复用而非复制** | §4.1 步骤 4 原写「直接 `setVolume(0.0)` + `pause()`」；实现改为给 `_fadeOut` 加 `immediate` 参数（`immediate \|\| !fadeEnabled` 走同一分支），避免复制一份静音逻辑 |
| 3 | **标记清理点落在 `_startPlayback()`** | 原清单列 `play()` / `playSong()` / `skipNext` / `skipPrevious` 四处；实测这些都收敛到 `_startPlayback()`（`play()`、`playSong()`、无声自愈、会话重激活都会经过它），一处插入即全覆盖 |
| 4 | **`silentByVolume` 加了 `_volume > 0.01` 守卫** | 否则用户把 App 内音量拉到 0 时，每次 `play()` 都会误报一次「无声自愈」（虽无害但污染诊断日志） |
| 5 | **iOS 未改动** | `handleInterruptions` 按 `defaultTargetPlatform` 传参，iOS 仍为 `true`；iOS 的打断链路（原生 `audioFocusGain` → `_smoothVolumeChange(_volume)`）本身正确，本次不碰 |
| 6 | **待真机确认** | §3.2 的结论「只有瞬时打断（`type=pause`）会踩中静音失联」来自库源码推断，尚未真机复现；§6.2 场景 1/2 即是该推断的验证 |
