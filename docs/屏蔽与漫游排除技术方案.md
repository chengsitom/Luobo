# 屏蔽与漫游排除技术方案

> 状态：**方案已确认**（2026-11-18），未开始编码
> 日期：2026-11-18
> 关联：`docs/多服务器管理与全量切换技术方案.md`（服务器/账号隔离口径）、`lib/services/auto_dj_service.dart`（漫游续播）

---

## 1. 背景与目标

曲库是**多人共用**的：一个道理鱼/Navidrome 账号下挂着全家人的音乐。这带来两类诉求：

1. **完全不听的内容**（某些歌手/专辑）：希望在自己的 app 里根本看不到，漫游、浏览、搜索都不出现。
2. **要保留但不参与随机的内容**（给儿子建的歌单）：歌单必须能打开、能播放，但**随机听歌时不要抽到**。

> 「删除」不是解法：曲库是共享的，删了别人就没得听，而且服务端删除不可逆。

**目标**：在不改动服务器数据的前提下，给每个（服务器, 账号）一份**本地视图过滤规则**，覆盖浏览、搜索、漫游、推荐、自动 DJ。

---

## 2. 方案选型

### 2.1 三种可能形态

| 方案 | 说明 | 结论 |
|---|---|---|
| A. 只做"排除随机" | 所有屏蔽只影响随机/漫游/推荐，列表照常显示 | ❌ 达不到"浏览时看不到他们" |
| B. 只做"完全隐藏" | 一律从所有列表/搜索/漫游移除 | ❌ 儿子的歌单会一起消失，丢掉核心场景 |
| **C. 两级模型** | `hidden`（隐藏）与 `muted`（仅排除漫游） | ✅ 采用 |

### 2.2 两级语义

| 模式 | 中文文案 | 列表/搜索 | 播放 | 漫游/随机/AutoDJ | 推荐/每日推荐/心动歌单 |
|---|---|---|---|---|---|
| `hidden` | **屏蔽**（彻底隐藏） | 不出现 | 不可播（从列表点不到） | 排除 | 排除 |
| `muted` | **仅从漫游排除** | 正常显示、可播 | 可播 | 排除 | 排除 |

**不变式：`hidden` 蕴含 `muted`。** 内部只存一个枚举，判定时 `isExcluded = mode == hidden || mode == muted`。

> 为什么推荐/每日推荐也归到 `muted`：它们本质就是"系统替我挑歌"，和漫游同源。用户说"不想随机听到"，推荐流同理。

### 2.3 作用对象

| 对象 | 阶段 | 说明 |
|---|---|---|
| 艺人 `artistId` | **P1** | 诉求 A：完全不听某些歌手 |
| 专辑 `albumId` | **P1** | 诉求 A 的细化 |
| 歌单 `playlistId` | **P1** | 诉求 B：儿歌**分散在多个艺人/专辑**上，无法用艺人/专辑近似，必须原生化 |
| 单曲 `songId` | P2 | 细粒度兜底，视 P1 使用情况再定 |

## 3. 数据模型

### 3.1 存储位置

本地 SQLite（复用 `DownloadDatabaseService` 所在库，或新建同库表），**不写服务端**。

```sql
CREATE TABLE blocked_content (
  server_id   TEXT NOT NULL,   -- 与封面缓存同一套 (服务器,账号) 命名空间
  user_id     TEXT NOT NULL,
  kind        TEXT NOT NULL,   -- artist | album | playlist | song
  target_id   TEXT NOT NULL,   -- 对应对象的服务端 id
  name        TEXT NOT NULL,   -- 冗余展示名（列表已同步不到时管理页仍可读）
  mode        TEXT NOT NULL,   -- hidden | muted
  created_at  INTEGER NOT NULL,
  PRIMARY KEY (server_id, user_id, kind, target_id)
);
```

### 3.2 为什么按 `(serverId, userId)`

- id 跨服不通用（Navidrome 与道理鱼各一套），按服隔离才不会张冠李戴。
- 多账号各自口味不同，换账号不该继承别人的屏蔽名单。
- 命名空间直接用现成的 `coverCacheServerId`（`lib/utils/image_cache.dart:68`），登录/切服/登出已在维护。

**已知取舍**：名单**只存本机**（已确认），同一账号的多台设备之间不同步。跨设备同步需要引入服务端约定或自建云，MVP 不做。

### 3.3 内存形态

`BlocklistService`：

```dart
class BlocklistService extends ChangeNotifier {
  Set<String> blockedArtistIds;  // hidden + muted
  Set<String> hiddenArtistIds;   // 仅 hidden（用于决定某对象"是否存在"）
  // 同理 album / playlist / song
  int get revision;              // 每次变更 ++，供外部缓存失效
  bool isSongExcluded(Song s);   // hidden ∪ muted 命中即 true
  bool isArtistHidden(String id);
  ...
}
```

## 4. 过滤点清单（工程核心）

> 原则：**只在读取/消费侧过滤，绝不改动 `_cachedAllSongs` 等原始字段**，也绝不写回数据库。
> 这样解除屏蔽零成本，且不影响下载/离线文件。

### 4.1 支点：曲库读取层

漫游、随机、全部歌曲、首页卡的候选池**全部来自 `LibraryProvider` 的 getter**：

- `cachedAllSongs`（`library_provider.dart:484`）
- `cachedAllAlbums`（`:466`）
- `artists`（`:502`）、`playlists`（`:456`）、`recentAlbums`（`:457`）、`randomSongs`
- `startRoaming()` 直接用 `library.cachedAllSongs` 当池（`player_provider.dart:4115`）
- AutoDJ 的本地池由 `setLocalPool(pool)` 注入（`player_provider.dart:4126`）

**在这些 getter 上做 memoized 过滤，即可一次性覆盖：漫游、随机播放、全部歌曲页、首页最近/常听/歌单区、AutoDJ 续播。**

### 4.2 逐点说明

| # | 位置 | 现状 | 改法 | 风险 |
|---|---|---|---|---|
| 1 | `LibraryProvider` 各 getter | 直出原始列表 | 返回过滤视图（memoized） | 计数"共 N 首"会跟着减少（符合预期） |
| 2 | `PlayerProvider.startRoaming()` | 用 `cachedAllSongs` | **无需改**（受益于 #1） | 池被过滤空 → 已有 `return false` 分支，提示"没有可播内容" |
| 3 | `AutoDjService.setLocalPool()` | 外部传入池 | **无需改** | ⚠️ 必须在注入前过滤。**不要**在 `_filterAndLimit` 里逐条过滤——会把池子抽干导致"漫游放着放着不续歌了"（该文件 `:374` 已记录过这个坑） |
| 4 | 服务端随机 `getRandomSongs` | 服务端返回 | 客户端二次过滤；不足则补拉一次 | 补拉后仍不足就少放，不空转 |
| 5 | 每日推荐 / 心动歌单 / 探索发现 | 服务端生成 | 获取后过滤；**过滤后为空则隐藏该区块** | 不能出现空白卡片或"0 首" |
| 6 | `SearchScreen` | 直出服务端结果 | 结果过滤 | 搜索是主要泄漏点，必须覆盖 |
| 7 | 艺人/专辑详情页 | 直接进 | 被 hidden → 显示"已屏蔽"占位页（含"解除屏蔽"按钮） | 避免从历史/通知点进来时白屏或 404 |
| 8 | 歌单详情 | 直接进 | 同上 | — |
| 9 | 已下载列表 / 本地音乐 | 列出全部 | **不屏蔽**：已下载/本地文件是"我自己占的磁盘"，管理优先于口味（已确认） | 屏蔽内容仍能在下载页看到并删除；漫游排除照样生效（排除是按 songId 判定的，与展示无关） |
| 10 | 最近播放 / 常听歌手 | 来自本地历史 | 展示时过滤 | 历史记录本身保留，解除后恢复 |
| 11 | 播放队列 | 已入队 | **不主动踢出**（避免打断正在听的） | 只影响后续挑选 |
| 12 | 设置 → 已屏蔽内容 | 无 | 新增管理页 | **唯一**的解除入口，必须做全 |

### 4.3 歌单特例：`muted` 需要成员展开

**先分清两件事，别混为一谈：**

| 数据 | 存在哪 | 需要网络吗 |
|---|---|---|
| 屏蔽关系（谁被屏蔽 / 哪种模式） | 本地 SQLite（§3.1） | **永远不需要** |
| 被排除歌单的**歌曲 id 集合** | 服务端（歌单成员） | 仅"从没打开过该歌单"时需要一次 |

原因：`getPlaylists()`（列表接口）只返回 id / 名字 / `songCount` / 封面，**不带成员**
（`subsonic_service.dart:1169`）；成员只在 `getPlaylist(id)` 详情接口里。
而 `loadPlaylistDetails()` 拿到带成员的 Playlist 后会写回 `_playlists` 并
`_saveCachedData()` **持久化**（`library_provider.dart:1333-1337`）——
**用户在 app 里打开过一次该歌单，成员就已经在本机了**。

选了「该歌单不进漫游」时：

1. 优先直接读本地 `playlists[id].songs`（打开过就有），**0 请求**；
2. 本地没有（从没打开过）→ `getPlaylist(id)` 拉一次，写入 `blocked_playlist_songs`；
3. 记录展开时的 `songCount` / `changed`，用于后续变化检测。

`hidden` 模式的歌单**不展开**：只让歌单条目消失，并同时把歌单 id 计入"排除漫游"（否则隐藏了个寂寞——歌还在曲库里随机得到）。

#### 4.3.1 成员保鲜：事件驱动 + songCount 检测，常态 0 请求

既然只有"成员集合"会过期，就不需要定时刷新，而是**在变化发生的地方修**：

| 时机 | 处理 | 请求 |
|---|---|---|
| 本机**加歌**进该歌单（`updatePlaylist(songIdsToAdd)` 成功） | 调用侧知道加了哪些 id → 直接追加进集合，并同步 `songCount` | **0** |
| 本机**删歌**（`updatePlaylist(songIndexToRemove)` 成功） | 调用侧知道删了哪首 → 直接从集合移除，并同步 `songCount`（不依赖接口返回值，那个不可靠） | **0** |
| 本机打开该歌单详情 | `loadPlaylistDetails` 已有成员 → 顺手覆盖集合 | **0**（本来就要拉） |
| 别处改了歌单（网页/另一设备） | `loadPlaylists()` 每次都会刷新列表，比对 `songCount`/`changed` 与记录值；**不一致才**重拉这一个歌单 | 仅变化时 1 次 |
| 兜底 | `expandedAt` 超过 7 天且上述都没触发 → 进漫游前静默重拉（失败沿用旧名单，绝不阻塞起播） | 极少 |

**因此常态是 0 请求**：屏蔽关系本地读写，成员要么已被打开动作带进来，要么在
`loadPlaylists()` 里免费检测到变化后才补一次。

> 之所以不做"每次进漫游前校验"：为了一条几乎不变的数据，每次起播都要多等一个
> 请求（远端 200~800ms），而且请求失败时的退化路径（用旧名单）与不校验完全一样
> —— 收益只在"刚在别的设备改完、当天立刻漫游"这一种情况，不值。

## 5. 性能

- 过滤是 `Set.contains` 的 O(n)，1 万首约 1ms 量级，但**绝不能每次 build 都算**。
- 缓存键：`(原始列表 identity, blocklist.revision, 数据版本)`；任一变化才重算。
- 歌单成员集合只在展开/刷新时变化，不进热路径。

## 6. 交互与文案

### 6.1 入口

| 位置 | 操作 |
|---|---|
| 艺人详情页 ⋮ | 「屏蔽此艺人」→ 底部选择：**彻底屏蔽** / **仅从漫游排除** |
| 专辑详情页 ⋮ | 「屏蔽此专辑」→ 同上 |
| 歌曲 ⋮ | 「屏蔽该艺人」/「屏蔽该专辑」→ 同上 |
| 歌单详情 ⋮ | 「屏蔽此歌单」/「此歌单不进漫游」→ 同上 |
| 设置 → 内容过滤 | 管理页：分组列出已屏蔽项，可切模式、可解除、可刷新歌单名单 |

### 6.2 文案要点

- 同一个入口，两档强度，弹窗里各带一句后果说明：
  - 彻底屏蔽：「在我的列表、搜索和漫游中都不再出现」
  - 仅从漫游排除：「仍然可以浏览和播放，只是不会被随机/推荐抽到」
- 管理页顶部一句总说明 + 当前生效数量，避免"我屏蔽了但好像没生效"。

### 6.3 是否给被 `muted` 的内容加角标

建议**不加**。`muted` 的内容本来就要正常使用，加标记只是噪音；用户想知道有哪些，去管理页看。

## 7. 边界与坑

1. **正在播放不打断**：屏蔽一个正在播的艺人，不切歌，只影响后续挑选。
2. **多艺人歌曲**：命中任一 `artistId` 即屏蔽；`artistId` 缺失时按 `artist` 名字兜底匹配。
3. **服务端生成内容过滤后为空**：隐藏整个区块，不能留空卡（每日推荐、心动歌单、探索发现）。
4. **漫游池被过滤空**：`startRoaming()` 返回 false，调用方提示"没有可播内容"（分支已存在）。
5. **搜索**：过滤后结果少于服务端总数，属预期；不做"已屏蔽 N 条"提示（会把屏蔽变成吸引力）。
6. **已下载文件**：不删文件、不删记录；**已下载页也不屏蔽**（已确认）——磁盘管理优先于口味，被屏蔽的歌仍能在下载页看到并删除。注意这一页的「随机/播放全部」是用户对着全量列表的显式操作，**不套用漫游排除**。
7. **切服/切账号**：名单按 `(serverId, userId)` 隔离，各自独立。
8. **解除路径必须完整**：被 `hidden` 的艺人在普通列表里点不进去，**唯一**解除入口是设置页——管理页是硬需求，不能省。
9. **歌单成员会变**：见 §4.3.1，靠「调用侧精确维护 + `songCount` 变化检测」保鲜；任何一次拉取失败都**沿用旧名单**继续用，绝不因为拿不到最新成员就阻断漫游起播。
10. **分页与计数**：服务端返回的总数含被屏蔽项，列表"共 N 首"按过滤后算。
11. **隐藏但不影响服务器**：任何路径都不得调用服务端删除接口。

## 9. 决策记录

已确认（2026-11-18）：

| # | 问题 | 结论 |
|---|---|---|
| 1 | 隐藏强度 | **彻底不可见**：列表、搜索、漫游都不出现；解除走设置页 |
| 2 | 搜索是否隐藏 | **也隐藏**，与列表口径一致 |
| 3 | 已下载里被屏蔽的歌 | **不屏蔽**（磁盘管理优先）；漫游排除照样生效 |
| 4 | 跨设备同步 | **不做**，名单只存本机 |
| 5 | 歌单成员保鲜 | **事件驱动 + songCount 检测**：屏蔽关系纯本地 0 请求；成员优先读本地（打开过就有），加/删歌在调用侧精确维护，`loadPlaylists()` 里用 `songCount` 免费检测变化，变了才拉。**不做定时刷新，也不做每次漫游前校验** |
| 6 | 歌单阶段 | **提到 P1**（儿歌分散，无法用艺人/专辑近似） |
| 7 | 入口默认档位 | **先弹选择**（彻底屏蔽 / 仅从漫游排除），不设默认 |

仍开放（不阻塞开工）：

1. **单曲粒度**（P2）是否真的需要——P1 上线后再看是否出现"只想排掉一两首"的诉求。
2. 管理页是否需要「屏蔽统计」（例：当前排除了 320 首、占曲库 3%）——有助于判断规则是否过宽，但也可能变成噪音。
