## 1. 背景与目标

道理鱼是一套**独立、闭源**的音乐服务系统（他人部署），对外提供**双协议**：

```
192.168.1.10:4000（内网） / music.example.com:10010（远程 HTTPS）
│
├── /rest/*.view   Subsonic 兼容层（Luobo 现用）
│     认证: 明文密码 p=（token+salt 被拒 code41）
│     能力: 浏览/搜索/播放/封面/歌单/收藏（子集）
│
└── /api/*         自研 JSON 层（JWT Bearer）
      认证: POST /api/auth/login → JWT
      能力: 歌词/随机歌/播放控制/推荐/Admin
```

目标：Luobo 以 `serverFamily='daoliyu'` 独立接入，登录后全部数据走道理鱼。由于道理鱼闭源无法改造，**所有适配均为 Luobo 客户端代码改动**。

> **2026-11-03 补充：远程地址是 IPv6-only（实测）**
>
> `music.example.com` **只有 AAAA 记录**（`2408:xxxx:xxxx:xxxx::1`，查 A 返回
> NODATA），由 **Lucky** 反代到 `http://192.168.1.10:4000`——家宽只有公网 IPv6
> 出口，这是既有架构前提。由此带来三条：
>
> 1. **无公网 IPv6 的网络完全连不上**（部分公司/校园 WiFi、部分宽带、多数 VPN+分流），
>    表现是"连接超时/服务器不可达"，**不要误判成域名失效**（`nslookup` 默认查 A，
>    对 AAAA-only 域名会报 "No answer"，就是这个坑）。
> 2. **AAAA 前缀会变**（电信动态前缀），必须由 DDNS 持续更新；否则某天会出现症状
>    完全相同的"连不上"。
> 3. 移动端走的就是这个地址，**不经过绿联 `*.ugdocker.link` 隧道**（隧道是 NAS
>    Web 桌面用的另一条路，前面有网关，裸 curl 会 302 到 NAS 登录页）。因此
>    `isUsingLocalUrl` 在家判定 LAN 正常，局域网免转码规则不受影响。

## 4. JWT 通道 + 歌词接入（核心改动）

### 4.1 新增能力（`subsonic_service.dart`）

```dart
String? _apiJwt;              // 内存 JWT
bool _apiLoginFailed = false; // 一次失败即标记，避免每首歌重复尝试登录

/// POST {activeBaseUrl}/api/auth/login
/// body: {"username": ..., "password": ...}
/// → 200 {token, user{...}}
Future<bool> loginToApi() async {
  if (_apiJwt != null) return true;
  if (_apiLoginFailed) return false;
  try {
    final resp = await _dio.post('$activeBaseUrl/api/auth/login',
        data: {'username': _config!.username, 'password': _config!.password});
    final data = resp.data as Map<String, dynamic>;
    final token = data['token'] as String?;
    if (token == null || token.isEmpty) return false;
    _apiJwt = token;
    _apiLoginFailed = false;
    return true;
  } catch (e) {
    _apiLoginFailed = true;
    Log.w('Daoliyu', 'API login failed: $e');
    return false;
  }
}

/// 带 Bearer 的 GET：401 → 重新 login 一次 → 重试
Future<Map<String, dynamic>?> _apiGet(String path) async {
  if (!await loginToApi()) return null;
  try {
    final resp = await _dio.get('$activeBaseUrl$path',
        options: Options(headers: {'Authorization': 'Bearer $_apiJwt'}));
    return resp.data as Map<String, dynamic>;
  } on DioException catch (e) {
    if (e.response?.statusCode == 401) {
      _apiJwt = null; // 过期，重登
      if (await loginToApi()) {
        final retry = await _dio.get('$activeBaseUrl$path',
            options: Options(headers: {'Authorization': 'Bearer $_apiJwt'}));
        return retry.data as Map<String, dynamic>;
      }
    }
    return null;
  }
}
```

> `_dio` 复用现有实例（`_configureCertificateValidation` 已重建），登录/歌词请求无需独立 Dio。
> 注意：自研层请求跟随 `activeBaseUrl`（LAN↔远程切换时用对应地址）。
>
> **状态重置**（易漏）：
> - `configure()` 时重置 `_apiJwt = null; _apiLoginFailed = false;`——换服务器后旧失败标记/旧 token 不得残留
> - `_setActiveBaseUrl()`（`subsonic_service.dart:87-91`）时重置 `_apiJwt = null`——LAN↔远程切换后 token 需按新地址重新登录

### 4.3 自研歌词响应转换

`GET /api/tracks/{id}/lyrics` 返回：

```json
{
  "trackId": "trk_...",
  "candidates": [ { "id": "MR", "syncType": "SYNCED",
                    "lyrics": "[00:00.00] 作曲 : ...\n[00:08.62]Let's start...\n[00:08.62]魔法开始显现\n...",
                    "lyricsPlain": "...", "available": true, "default": true } ],
  "preference": { "offsetMs": 0 },
  "effectiveCandidate": { ...同上... },
  "fallback": false
}
```

转换函数：

```dart
/// 取 effectiveCandidate.lyrics（LRC 格式，含中英交错），返回**双键**：
///   • lyrics           —— 原始 LRC（无损），供 LyricsManager 解析时间轴（车机副标题链）
///   • structuredLyrics —— 行数组 {start(ms), value}，供三个 UI 入口逐行渲染
/// 仅当 LRC 含有效时间轴行时才产出 structuredLyrics；纯文本时只返回 lyrics。
/// 见 `docs/歌词源优先级修复技术方案.md` §4 方案 C / §5.1。
Future<Map<String, dynamic>?> _getDaoliyuLyrics(String songId) async {
  final data = await _apiGet('/api/tracks/$songId/lyrics');
  if (data == null) return null;
  final candidate = data['effectiveCandidate'] as Map<String, dynamic>? ??
      ((data['candidates'] as List?)?.isNotEmpty == true
          ? (data['candidates'] as List).first as Map<String, dynamic>
          : null);
  if (candidate == null) return null;
  final lrc = candidate['lyrics'] as String?;
  if (lrc == null || lrc.isEmpty) return null;

  final result = <String, dynamic>{'lyrics': lrc};
  // LRC → 行数组：公共纯函数（P1 会替换 LRCLIB/网易云的私有等价实现）
  final lines = lrcToStructuredLines(lrc);
  if (lines.isNotEmpty) {
    result['structuredLyrics'] = [
      {'synced': true, 'line': lines},
    ];
  }
  return result;
}
```

> 解析实现落在 `lib/services/lyrics/lrc_parser.dart` 的 `lrcToStructuredLines()`（公共纯函数），不再内联一份。

- 道理鱼 LRC 是**原文/译文交错行**（同时间戳两行），`SyncedLyrics.fromLrc` / UI 解析器均按行渲染，天然支持双语显示
- `preference.offsetMs` 歌词偏移：**本迭代不接**（设置入口暂无对应 UI），保留扩展点

### 4.4 歌词取源链（道理鱼下）


|---|---|---|---|
| Subsonic `getCoverArt` | `/rest/getCoverArt?id=album:alb_xxx&size=` | max-age 86400 | 现有 `getCoverArtUrl()` 已用 ✅ 列表/播放页正常 |
| 自研层 coverArt | `/api/cover?path=...` | max-age=0 | 歌词/random 等自研响应里带的是这个 |

**结论**：正常浏览走现有 Subsonic 封面（已兼容）。只有自研层数据（random 歌单）里拿到的是路径式 coverArt——本迭代**不强求**其封面显示（随机歌列表可先不显示封面或用占位图），避免引入 ticket/路径式封面的额外逻辑。若体验需要再二期处理。

## 12. 与道理鱼 Web 实测能力的差距分析（2026-10-20）

> 本节为增量分析，不改变前 11 节的接入结论。实测对象：道理鱼 Web（`app-4000-<nas-id>.cn68.ugdocker.link`，v0.3.4/API 1.0.0），方法：CDP 注入 fetch/XHR 钩子 + `Network` 域抓请求/响应头 + 真实播放拖动。

### 12.1 先修订一个旧结论

> **⚠️ 2026-10-28 再次修订（真机直连实测，推翻本节 /stream 的 206 结论）**：对用户**当前连接的服务器 `app-4000-<nas-id>.cn35.ugdocker.link`**（经 chrome-cdp 在已登录的 Web 页内 `fetch` 实测），结论与下表 2026-10-20 的 `cn68` 抓包**不一致**——见本节末「§12.1-R 2026-10-28 cn35 实测」。**以 cn35 实测为准**：`/api/tracks/{id}/stream` 带 `Range` 头返回 **200 且无 `Accept-Ranges`**（不支持 Range）；HLS 则是完整可定位 VOD。下表中「`/stream` 始终可 Range」一行**已作废**。

原实现与代码注释（`subsonic_service.dart:791-795`、`player_provider.dart:3012-3015`）认为「道理鱼转码流不支持 HTTP Range，只能靠 `timeOffset` 重起流」。**实测后需修订为**：

| 取流状态 | 状态码 | Content-Range / Accept-Ranges | 结论 |
|---|---|---|---|
| `/api/tracks/{id}/transcode` **首次（无缓存）** | 200 | 无 / 无 | 实时管道，不可 Range 定位 |
| 同一 URL **完整产出并落缓存后** | 206 | `bytes 100000-100999/3548209` / `bytes` | 可 Range 精确定位 |
| `/api/tracks/{id}/stream` | 206 | `bytes 32768-7010011/7010012` / `bytes` | 始终可 Range |

拖动实测（播放中拖到 250s）：
- 转码（缓存已生成）：`Range: bytes=3964928-` → 206，立即 `seeked`；
- `/stream`：`Range: bytes=32768-` → 206，立即 `seeked`；
- HLS：`/api/tracks/{id}/hls` 返回 VOD m3u8，3 秒分片，由 hls.js 按分片定位。

**影响**：当前「道理鱼转码 seek 一律重起流」的策略在缓存命中时属于过度设计，代价是每次拖动重建音频源、维护 `_streamBaseOffsetMs`、重同步歌词。冷转码仍应保留 `timeOffset` 兜底。

> 尚未复测：Luobo 实际调用的 Subsonic 兼容端点 `/rest/stream?maxBitRate=128&format=mp3` 的 Range 行为（需 NAS 会话）。若其结果与 `/transcode` 一致，则可直接按缓存状态切换 seek 策略。

#### 12.1-R 2026-10-28 cn35 实测（直连覆盖旧结论）

方法：用户打开道理鱼 Web（`app-4000-<nas-id>.cn35.ugdocker.link/heart-playlists`），chrome-cdp 在页面登录态下 `fetch` 真实端点（token 取自 `localStorage['daoliyu.auth']`，流鉴权走 `?token=<JWT>`，与 Luobo 请求形状一致）。曲目取自 `/api/tracks/random`（返回 `{count, items[]}`，主键形如 `trk_…`）。

| 端点（带 `Range: bytes=100000-100200`） | 状态码 | Content-Type | Accept-Ranges | Content-Range/Length | 结论 |
|---|---|---|---|---|---|
| `/api/tracks/{id}/stream?token=…` | **200** | `audio/aac` | **无** | 无 / 无 | **不支持 Range**（chunked 管道）——**Luobo 现在播的就是这条** |
| `/api/tracks/{id}/stream?…&timeOffset=60` | 200 | `audio/aac` | 无 | 无 / 无 | timeOffset 被接受（200），仍是无 Range 管道 |
| `/api/tracks/{id}/transcode?token=…` | 200 | `audio/aac` | 无 | 无 / 无 | 冷转码 200 管道（未命中缓存） |
| `/api/tracks/{id}/hls?token=…` | **200** | `application/vnd.apple.mpegurl` | — | — | **完整 VOD m3u8** |

HLS 细节（278s 的曲目实测）：`#EXT-X-PLAYLIST-TYPE:VOD` + `#EXT-X-ENDLIST`（完整列表），**93 个 3s 分片，总时长 278s 正好对齐**（整首预切、任意位置可定位）；分片 URL 形如 `/api/tracks/{id}/hls/a192_3_c2_<hash>/seg_00000.ts?channels=2&hlsBitrate=192&quality=low&segmentDuration=3&token=…`；抽查首个 + 中间分片均 **`206 / video/mp2t / Accept-Ranges: bytes`**（分片本身可 Range）。

**定论**：
- `/stream`（Luobo 当前转码播放路径）在 cn35 上**不支持 Range** → ExoPlayer 无法字节 seek、断线重连从 byte 0 重取 = §13.14 倒带 bug 的**根因已坐实**；`subsonic_service.dart:979-981`「始终支持 Range、交给 ExoPlayer 原生 seek」的注释**对 cn35 为错**，待随 HLS 改造一并订正。
- **HLS 完整可用且 VOD 可定位** → 转码播放改走 `HlsAudioSource` 即可同时解决「转码 seek」与「断线重连倒带」。落地方案见 **§14**。

### 13.2 缺陷清单

**A. 策略层（根因）：Range 能力被误判，每次拖动重建一条转码流**

代码注释（`subsonic_service.dart:789-799`、`player_provider.dart:3038-3041`）认为「转码流 chunked、不认 Range」。实测（新文档 §5.1/§5.2）：

| 取流 | 状态码 | 能否 Range |
|---|---|---|
| `/api/tracks/{id}/stream`（**Luobo 实际播放的就是它**） | 206 | 始终支持 |
| `/api/tracks/{id}/transcode` 首次无缓存 | 200 | 不支持（实时管道） |
| 同一 transcode URL 落缓存后 | 206 | 支持 |
| `/api/tracks/{id}/hls`（VOD，3s 分片） | — | 由分片索引定位 |

代价：一次拖动 = 一次完整 re-buffer + 基准偏移 + 歌词重同步；连拖 N 次会给 NAS 起 N 条 ffmpeg（token 只作废客户端结果，服务端已开始的转码不会取消）。

**B. 偏移层：`_streamBaseOffsetMs` 只在两处生效**

`play()` 恢复路径取裸 `_audioPlayer.position`（`:2674`），随后 `seek(restorePos)`（`:2681`）；无声自愈同理（`:2719`、`:2803`）。重起流后这两处会把位置算成 `base + rawPos`，**往前跳**。

**C. UI 层：seek 后进度条不刷新 / 冻结 / 回跳**

- `seek()` 设了 `_position` 并 `notifyListeners()`（`:3028`），但**没有 `_positionController.add()`** → 依赖 `positionStream` 的播放页进度条只能等下一个 tick（暂停态不一定来）。
- 重起流时 `setAudioSource` 会推一个 0 位置的 tick，而 base 尚未设置 → `_position` 瞬间归零 → 迷你播放器进度环掉 0（对应《视觉与交互对标飞牛音乐技术方案》第五轮 ② 的「快进快退后进度环不动」）。
- `_waitingForSeek` 用百分比 5% 判定结束（`now_playing_screen.dart:3030`）：5 分钟曲目 = 15s、10 分钟 = 30s。既可能过早清除（条子一跳），也可能因落点差超 5% **永不结束**（条子冻在拖拽位置）。
- `onTapDown` 按下即 seek（`:3084-3091`），长按后再拖 → 先 seek 一次、松手再 seek 一次。

### 13.3 决策

> **⚠️ 2026-10-24 二次修订（真机证伪后）**：下面第 1、2 条的「Range 优先」已被真机否定 —— 播放器位置会落到目标（校验通过）但**音频从 0s 重放**，服务端 Range 只对浏览器成立。现行为：**道理鱼转码流一律 `restart`**，`native` 仅用于非道理鱼 / 直出原码流（详见 §13.13）。

1. ~~**Range 优先**~~（已修订）：原为「`target >= streamBase` 时先 native seek + 400ms 落点校验」。落点校验无法证明内容跳转，已删除该路径。
2. ~~**timeOffset 只作兜底**~~（已修订）：现为唯一 seek 路径。**新增服务端校验**：重起流加载后用 `loadedDuration` 判断 `timeOffset` 是否真的生效（剩余时长应 ≈ 总时长 − 目标），未生效则撤销基准、位置归零。

5. **进度条状态机**：绝对容差（1.5s）+ 超时兜底（2.5s）；`onTapUp` 替代 `onTapDown`；补 `onHorizontalDragCancel`。

### 13.12 真机反馈追加修复（2026-10-24）

**反馈现象**

1. 拖动进度条后，歌曲播完**不切歌**；并且从歌单页回到了首页（像触发了一次返回）。
2. 列表循环下播完**不播下一曲而是暂停**；播放页左显示歌曲时长、右显示 `-0:50`。

**根因 A：`_concatenatingSource` 残留 → 完成事件走 concat 分支**

- `_concatenatingSource` 只在 `clearQueue()`（`player_provider.dart:3662`）与有声书末章（`:1858`）清空，**单音源分支从不清理**。
- 只要本次会话先播过 gapless（默认开启，`_gaplessEnabled = true`），之后切到单音源模式（关闭 gapless / 道理鱼转码）时标记仍是旧值 ⇒ `_onSongComplete()` 走进 concat 分支 → `_handleEndOfQueue()`（AutoDJ 关闭时什么都不做）⇒ **播放停在 completed，表现为「暂停、不切歌」**。
- 串音源标记还会让 `skipNext / skipPrevious / skipToIndex` 对单音源执行 `seek(index:)`。
- **修法**：三处单音源建源（`playSong` 单曲分支、`_prepareCurrentSong` 单曲分支、`_restartDaoliyuStream`）显式 `_concatenatingSource = null`；`_onSongComplete` 增加 `identical(_audioPlayer.audioSource, _concatenatingSource)` 防御判定。

**根因 B：timeOffset 重起流的 duration 只是「剩余时长」**

- 重起流从 `base` 秒开始，播放器上报的 duration = 剩余秒数（例：3:00 的歌从 2:10 重起 → duration 0:50）。
- `effectiveDuration` 直接取 `_duration` ⇒ 进度条分母变短：左侧 `_position` 已是 3:00、右侧 `duration - position` = 0:50 − 3:00 → 显示 **`-0:50`**；`seekToProgress` 换算也会错位。
- **修法**：`effectiveDuration` 在 `_streamBaseOffsetMs > 0` 时返回 `流时长 + 基准`；`_updateAndroidAuto` / `_updateAllServices` 内重复的 duration 计算统一改为该 getter（此前各自用裸 `_duration`，锁屏/车机会显示剩余时长）。

**诊断增强**：`_onSongComplete()` 入口记录 `phase=songComplete`（`repeat / shuffle / queueLen / index / concat / concatActive / posMs / durationMs`）。若再次出现「播完不切歌」，先看该事件的 `concatActive` 与 `index`。

**仍需现场确认**：「从歌单页返回首页」在代码里找不到自动导航路径（全仓 `popUntil` 仅底栏 tab 点击触发）。待确认是否：① 系统返回手势（进度条左端起拖靠近屏幕边缘）；② 应用被系统重启（等同回到首页 + 播放恢复为暂停）；③ 播放页先被关闭再退了一层。诊断导出中 `meta.json` 的启动时间与 `trackNext/phase=songComplete` 是否连续即可判定。

### 13.14 转码流「断线重连倒带」自愈（2026-10-27）

**真机反馈（原话要点）**：「转码状态下播放一段以后，总是突然回跳到之前播放的位置。冷启从 12 分开始播，放到 16 分左右又跳回 12 分开始播」。

**根因**：道理鱼转码流不支持 Range，ExoPlayer 对这类 200 progressive 流**断线重连时从 byte 0 重取** → 引擎流内位置归 0。而 `_streamBaseOffsetMs` 仍是起播点（冷启续播 = 12 分），于是 `effective = 0 + base = 12 分`，音频也确实从 12 分重放 → 「播到一半跳回起播点」。这是流/ExoPlayer 行为，根治需服务端支持 Range 或改 HLS（见 §13.13 第 4 行）。

**客户端自愈**（`player_provider.dart` positionStream 监听）：识别「大幅回跳到 ≈ 流起点」的签名就按回跳前位置重起一条新流续回原处，而非任由倒带：
- 触发条件：`positionJumpedBack && _streamBaseOffsetMs>0 && isActiveStreamTranscoded && _isPlaying`，且 `effective ≤ base+1.5s`（回跳目标 ≈ 起播点，排除普通抖动），且回跳幅度 `> 5s`；
- 动作：记 `transcodeReconnectRewind` 诊断，`unawaited(_restartDaoliyuStream(回跳前的 _position))`，并 `return` 跳过本 tick（不把 `_position` 覆盖成起点，UI 不闪）；
- 防抖：`_lastTranscodeRewindRecovery` 4s 内不重复触发，避免密集重起。
- 正确性：新流 `setAudioSource` 推的 0-tick → `effective = 0 + 新base(回跳前位置)` = 续播点，不会再被判成回跳；用户主动 seek 走 `seek()` 先写 `_position` 故不误触发。

**验证**：`flutter analyze` 零 issue，`flutter test` 310 passed / 5 skipped。待真机确认：转码冷启续播放过起播点后不再倒带（诊断里应出现 `transcodeReconnectRewind`）。

> **2026-10-28 后续**：根因已被 §12.1-R 直连实测坐实（cn35 的 `/stream` 确为 200 无 Range）。本自愈是**兜底**；一旦转码播放改走 HLS（§14），分片级重连不再从 byte 0 重取，本倒带路径与 `transcodeReconnectRewind` / `_streamBaseOffsetMs` / `timeOffset restart` 一并可退役。

## 14. HLS 接入技术方案（2026-10-28，待拍板）

> 依据 §12.1-R 直连实测：cn35 的 `/api/tracks/{id}/hls` 是**完整 VOD**（ENDLIST、3s 分片全覆盖、分片 206 可 Range），而 `/stream` 是 200 无 Range 管道。本节把「转码播放改走 HLS」落成可执行设计。**先文档后代码**：定稿前不动代码。

### 14.1 目标 / 非目标

- **目标**：道理鱼**转码**播放改用 `HlsAudioSource(/api/tracks/{id}/hls)`，让播放器按分片原生 seek；消灭 §13.14「断线重连倒带」与「转码流 seek 无效」两类问题。
- **非目标**：① 非道理鱼 / `format=raw` 直出（局域网/无损）**不变**——它本就 Range 可 seek；② 不改服务端；③ 不引入新的音质切换 UI（沿用现有 `maxBitRate/format` 决策，只是取流换 HLS）。

### 14.2 现状 → 目标 的链路差

| 环节 | 现状（/stream + timeOffset restart） | 目标（HLS） |
|---|---|---|
| 取流 URL | `/api/tracks/{id}/stream?token=…[&timeOffset=N]` | `/api/tracks/{id}/hls?token=…`（返回 m3u8，分片 URL 自带 token） |
| 音源 | `AudioSource.uri`（progressive） | `HlsAudioSource`（just_audio） |
| seek | 转码 → `_restartDaoliyuStream`（重建流 + `_streamBaseOffsetMs`） | 播放器原生 `seek()`（分片定位），**无基准偏移** |
| 断线重连 | 从 byte 0 → 倒带（§13.14 自愈兜底） | 重取目标分片，天然续上 |
| 冷启续播 | `timeOffset` 起播 | 起播后原生 `seek(resumePosition)` |

- `subsonic_service.dart`：新增 `getDaoliyuHlsUrl(songId)` → `'$activeBaseUrl/api/tracks/$songId/hls?token=<JWT>'`（JWT 失败返回 null）。订正 `:979-981` 过期注释（/stream 非 Range）。
- `player_provider.dart`：
  - 取流决策：`_isDaoliyuTranscodeRequested` 为真 → 用 `HlsAudioSource(Uri.parse(hlsUrl))` 起播（`_prepareCurrentSong` 与 `playSong` 两处）；非转码/raw 维持 `AudioSource.uri`。
  - `seek()`：道理鱼转码**不再**走 `_restartDaoliyuStream`；`decideSeekPlan` 对「HLS 源」返回 `native`。保留 `restart` 仅作 HLS 不可用时的回退。
  - 退役（HLS 生效后）：`_streamBaseOffsetMs`、`_restartDaoliyuStream`、`transcodeReconnectRewind` 自愈、`timeOffset` 起播——分期移除，先并存加开关。
  - 冷启续播：HLS 源 `setAudioSource` 后 `_audioPlayer.seek(resumePosition)`（分片定位，无需 base）。
- `daoliyu_seek_policy.dart`：决策表加入「源类型 = HLS」维度，HLS → `native`。

### 14.4 鉴权与分片 token

- 实测分片 URL **自带 `token=<JWT>`**（与 playlist 同一个），ExoPlayer/AVPlayer 直接按 URL 取分片即可，无需自定义头。
- **风险**：JWT 过期 → 分片 401。需确认 token 有效期是否覆盖单曲/单章播放时长；长音频（有声书章节）尤其要测。若会过期，预案：播放前刷新 JWT、或 m3u8 代理层重写分片 token。**本期先实测有效期，不预先加代理**。
- **日志脱敏**：URL 带 token，诊断/日志里 token 必须打码（现有 `seekRestart*` 日志同样注意）。

### 14.5 平台与 just_audio 能力

- Android = ExoPlayer 原生 HLS、iOS = AVPlayer 原生 HLS，`HlsAudioSource` 直接支持；macOS/Windows（media_kit）需单测确认。
- m3u8 内分片是**相对 `/api` 路径**，`HlsAudioSource` 以 playlist URL 为 base 解析，需确认相对路径拼接正确（必要时服务端返回绝对 URL 或我们改写）。

### 14.6 有声书的特殊性（重点评估）

- 有声书现在走 `ConcatenatingAudioSource`（多章 gapless）。HLS 是**单章一条 m3u8**，与 gapless 拼接冲突。
- 选项：① 有声书暂不改 HLS（继续 /stream + 本章 timeOffset），只把**音乐**切 HLS；② 有声书改「每章一个 `HlsAudioSource` 进 Concatenating」，确认 just_audio 支持混入 HLS 子源与 gapless 表现。**建议先①**（音乐先行验证），有声书二期再评估。

### 14.10 起播慢 → 暂采方案 A（2026-10-28）

**真机反馈**：全程 HLS 后「歌曲起播很慢」。chrome-cdp 直连实测同一首歌 `/hls` 冷启动：拉 m3u8 **~3.9s** + 首个 3s 分片 **~3.1s** ≈ **出声前 7s**；服务端把该曲 HLS 热缓存后再请求则 m3u8 0.6s / 首段 3ms（快）。根因：① 本服务器首次 `/hls` 请求要现做转码规划，playlist 响应本身 ~4s；② HLS 必须等"整条 m3u8 + 第一个完整分片"就绪才出声，而 `/stream` 是连续管道、首批字节即可播（~1s 起播）。用户日常换不同曲→基本都是冷的→普遍 7s，代价每首都付。

**决策（用户选 A）**：起播回退 `/stream`（快），**不启用 HLS**；§13.14 倒带自愈继续兜底；转码 seek 回到「非字节级精确」的现状。

**实现**：新增开关 `PlayerProvider._hlsPlaybackEnabled = false`（`_trySetDaoliyuHlsSource` 首行短路）。§14 的全部管线（`getDaoliyuHlsUrl` / `HlsAudioSource` 起播 / `_isHlsSource` / seek 原生分支 / 冷启 HLS 恢复）**原样保留**，仅被开关关停——方案 B（起播 /stream、仅 seek 时切 HLS，首次 seek 慢几秒给服务端热 HLS、之后快）落地时把开关打开并把 HLS 起播改到 seek 路径即可。

**验证**：`flutter analyze` 0 error / 0 warning / 无 dead_code；`flutter test` **310 passed / 5 skipped**。起播恢复 `/stream` 快速路径，待真机确认起播速度回到改造前。
