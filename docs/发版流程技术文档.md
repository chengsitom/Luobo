# 发版流程技术文档（GitHub Actions 自动出包）

> 状态：**已实施**（2026-10-19，`.github/workflows/build.yml` 重写）
> 适用范围：Luobo（`chengsitom/Luobo`）全平台 Release 产出
> 关联：`docs/客户端接口与文档总览.md` §1 第 7 条「GitHub Releases 更新检查」、`lib/services/update_service.dart`

## 1. 背景与问题

别人开源项目「推个 tag 就自动出包」，Luobo 之前做不到，实测原因有四条：

1. **没有自动触发**——`build.yml` 只有 `workflow_dispatch`，必须手动点 Run workflow。
2. **Release 从未自动产出**——唯一一次运行（2026-09-23）`build-windows` 失败，而 `release` job 的 `needs` 是 5 个平台全量，于是一旦任一失败，Release 直接 skipped。
3. **失败被静默吞掉**——Android / Linux 构建命令写成 `flutter build ... | grep -v "$KEY" || true`，管道 + `|| true` 使退出码恒为 0。那次 Android 其实没产出 APK，job 却报 success，最后只留下一条 `No files were found` 警告。**「绿了但没包」是最危险的形态**。
4. **版本号与包内版本脱节**——`workflow_dispatch.inputs.version` 只用于打 tag，没有传给 `flutter build --build-name`；`installer.nsi` 也没收到版本号，Windows 安装器永远显示 `1.0.13`。

结果：仓库里 `v1.1.19` 这个 Release 存在，但 **assets 数量为 0**，点进去没有任何安装包。

## 2. 新的触发方式

```yaml
on:
  push:
    tags: ['v*.*.*']      # 推版本 tag 自动出包
  workflow_dispatch:       # 也可手动指定版本号
```

等价于两条路径：

- **路径 A（推荐）**：`git tag v1.1.20 && git push origin v1.1.20` → 自动跑全流程、自动建 Release。
- **路径 B**：Actions → Build & Release → Run workflow → 填 `1.1.20`。

> 在 GitHub 网页上「Draft a new release」创建 tag 同样会推送 tag，因而也会触发路径 A；随后 workflow 会更新同一个 Release 并补上 assets。两者不要同时点，`concurrency` 已按 ref 去重。

## 3. Job 结构

| Job | 作用 | 失败影响 |
|---|---|---|
| `prepare` | 解析版本号、**校验四处版本一致**、检查 secrets | 直接终止，不浪费构建机时 |
| `build-android` | 通用 APK + AAB | **硬门槛**，失败则不发 Release |
| `build-ios` | 未签名 IPA | **硬门槛**，失败则不发 Release |
| `build-windows` | NSIS 安装器 | `continue-on-error`，失败不连坐 |
| `build-linux` | tar.gz | `continue-on-error` |
| `build-macos` | DMG | `continue-on-error` |
| `release` | 汇总产物 + 建/更新 Release | `if` 要求 Android 与 iOS 均 success |

`release` 的守卫条件：

```yaml
if: ${{ !cancelled() && needs.build-android.result == 'success' && needs.build-ios.result == 'success' }}
```

桌面端历史上没在 CI 跑通过，先允许缺包；等 `build-windows` 稳定后再把 `continue-on-error` 去掉，恢复「全平台齐全才发版」。

## 4. 版本号一致性门禁

`prepare` 会读取并比对四处（见记忆/历史坑：v1.1.18 只改了 pubspec，另外三处漂移）：

| 位置 | 期望值 |
|---|---|
| `pubspec.yaml` | `version: X.Y.Z+N` |
| `lib/services/update_service.dart` | `currentVersion = 'X.Y.Z'` |
| `lib/main.dart` | `kAppVersion = 'X.Y.Z+N'` |
| `README.md` | `> **当前版本：vX.Y.Z**` |

任一处不一致，job 会打印「哪一处等于什么、应该改成什么」并失败，**不会产出错误版本的包**。

build number 取 `pubspec.yaml` 的 `+N`，不需要在 tag 里写。

## 5. 产物命名

| 平台 | 文件名 | 说明 |
|---|---|---|
| Android | `app-arm64-v8a-release.apk` | **绝大多数手机（推荐）**，只带 arm64 native 库 |
| Android | `app-armeabi-v7a-release.apk` | 老款 32 位手机 |
| Android | `app-x86_64-release.apk` | 模拟器 / ChromeOS |
| Android | `app-release.apk` | 通用包（含全部 ABI），不确定机型时用，体积最大 |
| Android | `app-release.aab` | 仅用于 Google Play 上传（不上传到 Release） |
| iOS | `luobo-ios.ipa` | 未签名 |
| Windows | `musly-setup.exe` | |
| macOS | `luobo-macos.dmg` | |
| Linux | `luobo-linux-x64.tar.gz` | |

> Windows/macOS 的内部标识（`musly.exe`、`musly.app`）仍是上游名，属于原生工程标识，本轮未改，避免影响已安装用户的升级路径。

### 5.1 Android 正式签名

release 包必须用正式 keystore 签名：

- **本地**：`android/key.properties` + `android/app/luobo-release.jks`（两者都被 `.gitignore` 排除）
- **CI**：只需 `ANDROID_KEYSTORE_BASE64` + `ANDROID_KEYSTORE_PASSWORD` 两个 secrets；**别名由 keytool 自动探测**，**key 密码直接复用 store 密码**（keystore 是 PKCS12，key 与 store 密码必须相同，单独配置 `ANDROID_KEY_PASSWORD` 反而因粘贴带空格引发 `Given final block not properly padded`）

`android/app/build.gradle.kts` 在缺少 `key.properties` 时**直接抛 `GradleException`**，不会回退 debug keystore。CI 还额外执行 `apksigner verify --print-certs`，发现 `CN=Android Debug` 就中止发布。

> ⚠️ **keystore 一旦丢失去，已安装用户将永远无法覆盖升级**（包名相同但签名不同，Android 会拒绝安装）。请把 `luobo-release.jks` 和密码离线备份（密码管理器 / 加密云盘），不要只留在本机。

## 6. 首次发版操作步骤

1. 四处处版本号一起改成目标值（例如 `1.1.20` / `+15`），提交并推送。
2. `git tag v1.1.20 && git push origin v1.1.20`。
3. 到 Actions 看 `Build & Release`：`prepare` 通过后 5 个平台并行构建。
4. 构建完成后自动出现 Release，assets 应包含 4 个 Android APK / IPA（以及成功的桌面端包）。
5. App 内「检查更新」读的是 `releases/latest`，新 Release 发布后即可生效（`update_service.dart` 比对 `currentVersion`）。

## 7. 已知限制 / 二期

- **iOS**：macOS runner 只做 `--no-codesign`，产出未签名 IPA，用户需 AltStore / Sideloadly 侧载。
- **桌面端**：Windows job 曾在 CI 失败且日志需 admin 权限才能取；本轮照搬上游 Musly 的 `CL/_CL_` 抑制宏与显式 `$LASTEXITCODE` 校验，2026-10-19 首次运行已成功。
- **Release 文案**：由 README 版本历史自动提取（与 App 内更新日志同源），不再从 `CHANGELOG.md` 取，因为该文件停留在上游 v1.0.13。
- **签名切换**：v1.1.20 之前发布的 APK 是 debug 签名，用户升级到 v1.1.21+ 的正式签名包时需**先卸载旧版**一次；此后可正常覆盖升级。
