# Luobo 车机媒体会话与歌词推送技术方案

> 状态：**P0/P1 已实施（2026-09-23）** —— `flutter analyze` 零 error/warning、`flutter test` 182 绿 / 5 跳过（含新增 5 条）、原生 Kotlin 改动 `flutter build apk --debug` 编译通过；**待真机/车机验证**（§6.3）
> 范围：Android 端「车机侧」的三条链路 —— ① 媒体信息（标题/歌手/封面/进度）② 上一曲/下一曲（transport 回调）③ 歌词（副标题行）；**不含 App 内的「车载模式」UI（`car_mode_screen.dart`），两者互不影响**
> 依据：Luobo master（v1.1.17）源码实证 + 上游 `dddevid/Musly` 历史提交（`1edeebb` / `a5b3138` / `6a0c409b`）
> 触发问题：用户用 **CarLife** 连车机（App 无法在车机展示属正常），观察到「别的音乐 App 播放时车机能显示歌词，Luobo 不能」「车机上一曲/下一曲无法控制 Luobo」
> 关联（2026-10-08 增补）：**本文件描述的「推送链路」已通**。用户 2026-10-08 再次反馈「App 投射到车机上时副标题没有展示成歌词」，实测「手机通知栏第二行显示歌手名」⇒ 问题在**取源侧**（车机链只有 `getLyricsBySongId` 一条来源、不读缓存），见 `docs/歌词源优先级修复技术方案.md` §2.6（P0 已实施）。**判据**：通知栏第二行滚歌词而车机不显示 ⇒ 才是本文件的「车机读法」问题（§4.4）。

---

## 1. 背景与现象

用户在车机上通过 CarLife 连接手机，Luobo 播放时：

| 现象 | 用户描述 | 本文结论 |
|---|---|---|
| App 界面不能显示在车机上 | 「app 不能在上面展示」 | **正常现象**：未接入 CarLife SDK，车机只会显示通用媒体卡片（见 §4.4） |
| 车机不显示歌词 | 「别的音乐 app 可以展示歌词」 | **缺陷**：原生链路完整，Dart 侧推送被上游重构删掉（P0，§3.1） |
| 上一曲/下一曲无效 | 「不能被汽车的上一曲、下一曲按钮控制」 | **缺陷**：四跳链路中两处静默丢弃 + 接线竞态（P1，§3.2） |

> 一句话：**第一条是平台限制，第二、三条是我们自己的实现缺口**，且根因都能定位到具体代码位置。

---

## 2. 三条链路的来源（代码实证）

车机上看到的/能操作的东西，来源是**三个独立机制**，必须分开看：

| 车机上的东西 | 数据来源 | 标准能力？ | Luobo 现状 |
|---|---|---|---|
| 标题 / 歌手 / 封面 / 进度 | `MediaSession` 的 `MediaMetadata`（蓝牙 AVRCP 或 CarLife 读 session） | 是 | ✅ 正常 |
| 上一曲 / 下一曲 / 播放暂停 | `MediaSession` 的 transport 回调 | 是 | ⚠️ 链路存在但不可靠（§3.2） |
| **歌词** | **不是标准字段**。做法是把当前歌词行写进 `MediaMetadata.DISPLAY_SUBTITLE`（副标题），车机当第二行显示；或接入 CarLife SDK 的专用通道 | 否（需 App 主动上报） | ❌ Dart 侧从未上报（§3.1） |

### 2.1 Android 侧媒体栈现状

| 层 | 实现 | 位置 |
|---|---|---|
| 音频播放 | Dart `just_audio`（ExoPlayer） | `lib/providers/player_provider.dart` |
| **MediaSession / 通知栏 / Android Auto 浏览树** | **原生自研** `MusicService.kt`：`MediaBrowserServiceCompat` + `MediaSessionCompat("LuoboMusicService")` + 自建通知 | `android/app/src/main/kotlin/com/musly/musly/MusicService.kt` |
| Dart ↔ 原生通道 | `com.devid.musly/android_auto`（MethodChannel）+ `com.devid.musly/android_auto_events`（EventChannel） | `AndroidAutoPlugin.kt` / `lib/services/android_auto_service.dart` |
| 歌词 → 原生 | `com.devid.musly/lyrics`（MethodChannel） | `LyricsPlugin.kt` / `lib/services/lock_screen_lyrics_service.dart` |
| `audio_service` 包 | **Android 上刻意不初始化**（避免第二个 service 与 MusicService 抢 session） | `lib/services/audio_handler.dart:193-208`（注释明确写明） |
| Manifest | `.MusicService`（`exported=true` + `MediaBrowserService` intent-filter，`AndroidManifest.xml:85-97`）、`MediaButtonReceiver`（`:100-106`）、`com.google.android.gms.car.application` meta-data（`:58-59`） | `android/app/src/main/AndroidManifest.xml` |

> 关键结论：**Android 上的车机能力全部压在这套自研原生桥上**，`audio_service` 的现成能力（MediaButtonReceiver、skip 映射、`MediaItem.displaySubtitle`）在 Android 侧完全没被用上。

## 3. 根因

### 3.1 歌词：原生链路完整，Dart 侧断链（P0）

**原生侧是完整实现**（这也是「别的 App 能显示歌词」的同款机制）：

| 环节 | 位置 | 说明 |
|---|---|---|
| 通道入口 | `LyricsPlugin.kt:48-51` | `updateLyrics`，参数名 **`currentLine`** |
| 写入副标题 | `MusicService.kt:590-592` | `putString(METADATA_KEY_DISPLAY_SUBTITLE, currentLyricsLine)` |
| 通知栏副标题 | `MusicService.kt:749-753` | 通知第二行优先显示当前歌词行 |
| 入口方法 | `MusicService.kt:917-927` | `updateLyrics()` → 刷新 metadata + 通知 |

**但 Dart 侧从来没调用过它。** `lib/services/lock_screen_lyrics_service.dart:164-182`：

```dart
Future<void> _updateLockScreenLyrics(String line) async {
  if (line == _lastSentLine) return;
  _lastSentLine = line;
  // Live Activity 更新已为 iOS 15 兼容注释掉
  // Update Windows notification lyrics
  if (supportsWindowsNotification) {   // Android 上恒为 false
    await _windowsService.updateLyrics(line);
  }
}
```

全仓 `grep "invokeMethod('updateLyrics'"` → **零结果**；`_clearLyrics()`（`:90-109`）同样只清 Windows，而 `clearAllLyrics()`（`:214-230`，内含唯一的 `invokeMethod('clearLyrics')`）**全仓无调用点**。

同步逻辑本身是活的（不是「没做」）：
- `player_provider.dart:2495-2498` → `loadLyrics(lrc)` + `startSync(positionStream)`
- `startSync`（`:113-153`）每 500ms 节流算出当前行 → `_updateLockScreenLyrics(line)` → **发不出去**

**根因提交（上游，非本 fork 引入）**：

- `1edeebb`（2026-05-04，dddevid）`Enable lyrics on Android via live_activities package`：commit message 原文含 *"Removed separate Android MethodChannel path for lyrics updates"* —— 把 Android 的 `invokeMethod('updateLyrics')` 整段删除，改为走 `live_activities` 包
- 后续为兼容 iOS 15，所有 `_liveActivities.*` 调用被注释掉（现文件中的注释块）
- **净结果：Android 上一条路都不剩**，原生 `DISPLAY_SUBTITLE` 机制变成死代码；本 fork 于 2026-06-22 分叉时继承了该回归

> 影响面不止车机：**Android 通知栏副标题也一直没有歌词**（同一根因）。

### 3.2 上一曲/下一曲：四跳链路 + 两处静默丢弃（P1）

链路（Android）：

```
车机按键
 └─ MusicService.MediaSessionCallback.onSkipToNext()      MusicService.kt:858-864
     └─ AndroidAutoPlugin.sendCommand("skipNext")          AndroidAutoPlugin.kt:220-225
         └─ eventSink?.success(data)   ← EventChannel      ← 静默丢弃点 ①
             └─ Dart _handleEvent case 'skipNext'          android_auto_service.dart:87-92
                 └─ onSkipNext → PlayerProvider.skipNext()  player_provider.dart:555 / 3005
```

`skipNext()` / `skipPrevious()`（`:3005` / `:3175`）实现完整（队列、shuffle、repeat、有声书分支都处理了），**问题都在它前面**：

| # | 问题 | 位置 | 后果 |
|---|---|---|---|
| ① | `eventSink?.success(data)` —— sink 为 null 时**静默丢弃，无日志** | `AndroidAutoPlugin.kt:224` | Dart 侧订阅未建立/被取消（热重启、引擎重建、`initialize()` 早期抛错）时，车机所有按键「按了没反应」，且无任何报错 |
| ② | `initialize()` 在回调赋值**之前**调用 | `player_provider.dart:549-566` | 启动窗口期内到达的命令遇到 `onSkipNext == null`，同样被丢弃 |
| ③ | session 可能失效：`onTaskRemoved` 置 `isActive=false` + `stopSelf()`，服务 `START_NOT_STICKY` | `MusicService.kt:937-952` / `:104-108` | 划掉最近任务/系统回收后，车机再也控制不到 Luobo |
| ④ | 结构性：上游 `a5b3138`（2026-07-15）已把这套自研桥**整体删除**，改为 `audio_service` 承载 MediaSession | 上游提交 | 说明该设计本身被上游判定为不可靠（见 §4.3） |

> ①②③ 属于「不确定哪一条在用户车上生效」——因此本文的 P1 除了加固，还要**补日志锚点**（§6.2），让一次上车就能定位。

## 4. 方案

### 4.1 P0：补回 Android 歌词推送（采用，最小改动）

在 `LockScreenLyricsService` 补回原生推送，并明确平台判定：

- 新增 `supportsAndroidNotification`，用 `defaultTargetPlatform == TargetPlatform.android` 判定（**而非 `Platform.isAndroid`**：便于单测用 `debugDefaultTargetPlatformOverride` 覆盖）
- `_updateLockScreenLyrics()`：Android 分支 → `invokeMethod('updateLyrics', {'currentLine': line})`（参数名必须与 `LyricsPlugin.kt:49` 一致）
- 新增私有 `_clearNativeLyrics()`：Android 下 `invokeMethod('clearLyrics')`，供两处复用 ——
  - `loadLyrics(lrc)` 换歌时先清一次，避免上一首的歌词行挂到新歌上（新行由 `startSync` 随位置推送）
  - `loadLyrics(null)` / `_clearLyrics()`（无歌词、异常兜底）清掉残留行
- `clearAllLyrics()` 改为委托 `_clearLyrics()`：原先自带一份原生清理且**不复位** `_currentLyrics`（残留行会被重新推上去），现在统一走一条路径
- 保留既有 500ms 节流与 `_lastSentLine` 去重，避免高频刷新通知

```dart
// _updateLockScreenLyrics 内，Windows 分支之前
if (supportsAndroidNotification) {
  try {
    await _platform.invokeMethod('updateLyrics', {'currentLine': line});
  } catch (e) {
    debugPrint('[Lyrics] Failed to push lyrics to native: $e');
  }
  return;
}
```

### 4.2 P1：命令缓冲 + 接线顺序（采用）

**原生（`AndroidAutoPlugin.kt`）**：`eventSink` 为空时把命令入队，订阅建立后重放；带 TTL 与容量上限，避免「App 重开后重放几秒前的旧按键」：

- `PendingCommand(command, arguments, queuedAt)` + `ArrayDeque`
- `onListen` → 设置 sink 后 `flushPendingCommands()`
- flush 时丢弃 `now - queuedAt > 5000ms` 的过期命令；队列上限 32 条（超出丢最旧）
- 全链路补日志（英文，与该 Kotlin 文件既有风格一致）：`sendCommand(x) -> Flutter` / `Flutter not listening, buffered (n pending)` / `flushPendingCommands: replayed n, dropped m expired`

**Dart（`player_provider.dart:_initializeAndroidAuto`）**：把 `initialize()` 移到所有回调赋值**之后**，消除启动竞态 ②。

### 4.3 方案对比：为什么不直接照搬上游 `a5b3138`

| 方案 | 做法 | 成本 | 结论 |
|---|---|---|---|
| **A. 最小修复**（P0+P1） | 补 Dart 歌词推送 + 命令缓冲 + 日志 | 低（2 个 Dart 文件 + 1 个 Kotlin 文件） | ⭐ 采用：先让能力生效并能定位 |
| B. 迁移到 `audio_service` | 按上游 `a5b3138` 删除 `MusicService.kt` / `AndroidAutoPlugin.kt`，Android 也走 `AudioService.init`，用 `MediaItem.displaySubtitle` 上报歌词行、`skipToNext/skipToPrevious` 由 audio_service 映射 | 中高：需拆掉自研桥与双 session 风险，回归面覆盖通知/锁屏/Android Auto/UPnP 远程音量 | 二期候选（§8.1） |
| C. 接入 CarLife SDK | 走百度 CarLife 第三方 SDK（2015 年起的方式，如喜马拉雅接入） | 高：SDK + 通常需车厂/百度认证 | 仅当 §4.4 确认车机不读副标题时才评估 |

### 4.4 待确认前提（决定「修完能不能真看到歌词」）

车机第二行读的是 **MediaMetadata 副标题**，但**不同车机对副标题的支持不一致**：有的显示、有的只显示标题+歌手。另需区分车机显示的是**蓝牙音乐卡片**（读 AVRCP）还是 **CarLife 音乐卡片**（读 MediaSession），两者来源不同。

因此验收口径：

- 修完上车后 **第二行开始滚歌词** → 链路通，收工
- 第二行仍是歌手名 / 无变化 → 该车机不读副标题，转方案 C（接 SDK）或放弃车机歌词

### 6.2 上车定位法（一次 logcat 就能定位断点）

```bash
adb logcat | grep -E "MusicService|AndroidAutoPlugin|AndroidAuto command|Lyrics"
```

| 现象 | 结论 |
|---|---|
| 有 `sendCommand(skipNext) -> Flutter`，无 `AndroidAuto command received: skipNext` | 断在 EventChannel → Dart（查 sink/订阅） |
| 有 `AndroidAuto command received: skipNext` 但歌不换 | 断在 `PlayerProvider`（队列为空等状态问题） |
| 连 `MusicService onStartCommand` 都没有 | 车机根本没打到我们的 session（③） |
| 有 `Updated lyrics via MusicService: xxx` 但车机不显示 | 车机不读副标题 → §4.4 方案 C |

### 6.3 真机清单

1. 播放有逐行歌词的歌曲 → Android **通知栏副标题**随歌词滚动（P0 的直接可验证点，不依赖车机）
2. 无歌词/纯音乐 → 副标题回落到歌手名，无残留旧歌词行
3. 切换歌曲 → 副标题立即清空后重新滚动，不出现上一首的歌词
4. 车机（蓝牙或 CarLife）连接 → 第二行是否显示歌词（§4.4 判定）
5. 车机上一曲/下一曲 → 生效；若无效，按 §6.2 取日志

## 7. 风险与回滚

| 风险 | 应对 |
|---|---|
| 高频 `updateLyrics` 造成通知/元数据频繁刷新 | 保留 500ms 节流 + `_lastSentLine` 去重；原生侧 `updateLyrics` 对相同行直接 return（`MusicService.kt:918`） |
| 命令缓冲导致旧按键延迟生效 | TTL 5s + 上限 32 条，过期直接丢弃并记日志 |
| 车机不读副标题（预期内） | 不影响 App 内与通知栏；不引入新依赖，最坏是「车机仍无歌词」 |
| Kotlin 改动未编译验证 | 落地后执行一次 `flutter build apk --debug`（或 CI）确认编译 |

**回滚**：改动集中在 3 个源文件 + 1 个新测试，均无数据结构/持久化变更，git 单 commit 可整体回退。

## 8. 后续（P2 候选，不在本次范围）

1. **迁移 MediaSession 到 `audio_service`**（对齐上游 `a5b3138`）：收益是 skip 映射、`MediaItem.displaySubtitle` 上报歌词、Android Auto 浏览树全部由库提供；代价是拆除 `MusicService.kt` 自研桥，必须同时处理双 session 与通知/锁屏/UPnP 远程音量回归。
2. **CarLife SDK 接入评估**：仅当 §4.4 判定车机不读副标题时才立项（含认证成本）。
3. **session 保活**：`onTaskRemoved` 后 session 失效（③）是否要改为保活，取决于是否期望「App 划掉后车机仍可控制」。
