# Luobo 歌词源优先级修复技术方案

> **范围**：歌词的**取源与消费**链路 —— 服务层 `getLyricsBySongId()` + 4 个消费入口（含**车机副标题 / 通知栏 / 锁屏**）+ 本地歌词缓存。
> **不含**歌词渲染 / 滚动 / 视觉（属 `docs/歌词页视觉对齐苹果设计技术方案.md`），不含歌词偏移（`preference.offsetMs`，见 `docs/道理鱼接入技术方案.md` §11 已挂账）。
>
> **触发问题（两次，互为镜像）**：
> 1. 用户 2026-10-08「我是发现很多歌词明显不是道理鱼返回的」（当时 LRCLIB 与网易云两个兜底开关**均为开启**）→ **服务器有歌词，UI 却显示兜底歌词**（§2.1-2.4）
> 2. 用户 2026-10-08「App 投射到车机上时，副标题没有展示成歌词」，实测三问：车机上是**媒体卡片第二行** / **手机通知栏第二行显示歌手名** / App 内歌词页能逐行滚动 → **服务器无歌词时，车机链一条都拿不到**（§2.6）
>
> **状态**：**P0 已实施（2026-10-08）** —— §8 六项决策全部拍板并落地：`flutter analyze` 零新增 error/warning、`flutter test` **243 通过 / 5 跳过**（含新增 `test/services/lyrics_source_test.dart` 36 条）；**待真机验收**（§7 真机清单，尤其第 7-9 项）。P1 未做。
> 关联：`docs/车机媒体会话与歌词推送技术方案.md`（推送链路，已通）、`docs/道理鱼接入技术方案.md` §4、`docs/客户端接口与文档总览.md` §3。
> 合并说明：另有一份《歌词来源统一技术方案》描述同一子系统，已于 2026-10-08 **合并进本文并删除**，保持单一事实来源。

## 1. 现象与结论

**一句话结论（两个方向）**：

- **方向一（§2.1-2.4）**：道理鱼的歌词**确实被请求了**，但被三个 App 内入口丢掉，最后由 LRCLIB / 网易云顶替；顶替结果又会写进本地缓存并排在服务器查询之前，形成**永久占位**。
- **方向二（§2.6）**：反过来，服务器**没有**歌词时，车机链**没有任何兜底可落** —— App 内靠网易云显示歌词，通知栏与车机副标题却一条都拿不到（回落歌手名）。

| 入口 | 用户观察 | 实际歌词来源 |
|---|---|---|
| 全屏歌词页 `SyncedLyricsView` | 不是道理鱼的（整段英文 / 对不上 / 无双语） | **LRCLIB（先）或网易云（后）** |
| 播放页内嵌 `CompactLyricsView` | 一直「无歌词」 | 无（无兜底，服务器结果同样被丢） |
| 车载模式页 `CarModeScreen` | 同全屏歌词页 | LRCLIB / 网易云 |
| **车机副标题 / 通知栏 / 锁屏** | 「正常（道理鱼）」—— 见下方注 | **道理鱼（唯一源，无兜底）** |

最后一行曾是**关键对照组**：同一条 `getLyricsBySongId()`，车机那条链拿到的是道理鱼歌词，UI 那条链拿到的是兜底歌词 —— 说明问题不在「请求」，在「消费」。

> ⚠️ **该对照组只在「服务器有歌词」的歌上成立**（2026-10-08 二次增补修正）。服务器无歌词时，车机链同样一条都拿不到 —— 用户 2026-10-08 实测「手机通知栏第二行显示歌手名」即是该情形。详见 §2.6。

## 2. 根因（代码实证）

### 2.1 服务层返回「双形态之一」，只有一条链认它

`_getDaoliyuLyrics()`（`subsonic_service.dart:1300-1321`）取 `effectiveCandidate.lyrics`（LRC 文本）后返回：

```dart
return {'lyrics': lrc};   // subsonic_service.dart:1315
```

这是**刻意**的（`:1293-1297` 注释）：`player_provider._convertStructuredToLrc`（`:2521-2536`）读的是 Jellyfin 的 `{startTicks, text}` 字段，若返回 `{start, value}` 会产出空行（此前真机确认的 bug）。

但该注释只列了**一个**消费者（`player_provider._loadAndSyncLyrics`），另外三个入口**没有同步适配**。

### 2.2 三个 UI 入口只认 `structuredLyrics` / `value`

| 入口 | 代码位置 | 认的键 |
|---|---|---|
| 全屏歌词页 | `synced_lyrics_view.dart:316-347` | 仅 `structuredLyrics` |
| 播放页内嵌 | `compact_lyrics_view.dart:120-151` | 仅 `structuredLyrics` |
| 车载模式页 | `car_mode_screen.dart:129-163` | 仅 `structuredLyrics` |

`{'lyrics': lrc}` 里没有 `structuredLyrics` 键 → 三者一律判定「无同步歌词」→ 落到各自的下一步。

### 2.3 下一步必然落空，再下一步就是外部源

三个入口的下一步都是 `getLyrics(artist, title)`（`subsonic_service.dart:1246-1266`）→ Subsonic `/rest/getLyrics`。

道理鱼的 Subsonic 兼容层**不提供歌词能力**：`docs/道理鱼接入技术方案.md:43` 实测 `getLyricsBySongId` → `Unknown endpoint`。`getLyrics` 未单独实测，但**由 §1 的对照组可反推其同样不可用** —— 若它返回了道理鱼歌词，UI 就会显示道理鱼（纯文本）歌词，用户也就不会看到兜底歌词。

→ `_request` 因 `status != ok` 抛错 → `getLyrics` 返回 null。于是进入：

```
LRCLIB（synced_lyrics_view.dart:368-425）→ 网易云（:427-483）
```

**顺序是 LRCLIB 在前、网易云在后**（`car_mode_screen.dart:192` / `:260` 同构）。开关默认值：LRCLIB **默认关**（`storage_service.dart:164` `?? false`）、网易云**默认开**（`:174` `?? true`）。本例两者都开 → 实际命中以 **LRCLIB** 为主。

> 补充：LRCLIB 是社区众筹库、以欧美曲库为主，中文歌覆盖差，是三个源里体验最差的。它排在网易云之前，所以中文歌的兜底歌词也先经过它。

### 2.4 缓存把「顶替」变成「永久」

兜底结果会被写进本地离线歌词缓存（`synced_lyrics_view.dart:386`、`:444`；`car_mode_screen.dart:210`、`:277`）：

- 缓存文件：`<offlineDir>/<songId>.lyrics.json`（`offline_service.dart:81-114`），内容形如 `{'lyricsList': <map>}` / `{'lyrics': <map>}`；
- 读取时**排在服务器查询之前**（`synced_lyrics_view.dart:316`）；
- **不带来源标记**，无法区分「服务器歌词」与「兜底歌词」。

→ 一首歌一旦被 LRCLIB 命中并缓存，之后**连道理鱼的接口都不会再问**。这就是为什么是「**很多**」而不是「偶尔」。

### 2.5 文档与代码已不一致（需一并同步）

`docs/客户端接口与文档总览.md:90`、`:110` 与 `docs/道理鱼接入技术方案.md:190-241`、`:409` 均写「取 `effectiveCandidate.lyrics` → **转 structuredLyrics**」，与 `subsonic_service.dart:1315` 的实际实现相反。

### 2.6 镜像缺口：服务器无歌词时，车机链一条都拿不到（2026-10-08 二次增补）

§2.1-2.4 是「服务器**有**歌词、UI 丢掉」；本节是它的镜像 ——「服务器**没有**歌词、车机链没有兜底」。

**车机链的取源只有 1 级**（`player_provider._loadAndSyncLyrics`，`player_provider.dart:2463-2518`）：

| 级 | 来源 | 行号 |
|---|---|---|
| 1 | `subsonicService.getLyricsBySongId(id)` | `:2476`（**唯一来源**） |

对比全屏歌词页（`synced_lyrics_view.dart:303-500`）：

| 级 | 来源 | 行号 |
|---|---|---|
| 1 | 本地缓存 `offlineService.getLocalLyrics(songId)` | `:311-312` |
| 2 | `getLyricsBySongId(id)` | `:317` |
| 3 | `getLyrics(artist, title, id)` | `:337-339` |
| 4 | LRCLIB 兜底（开关默认关） | `:370-425` |
| 5 | **网易云兜底（开关默认开）** | `:428-480` |

**后果**：凡是靠「网易云兜底 / 本地缓存 / 纯文本」拿到歌词的歌 —— App 内正常逐行滚动，车机链**一条都拿不到**：

```
_loadAndSyncLyrics 拿到 null → loadLyrics(null)（player_provider.dart:2505/2510）
  → LockScreenLyricsService.startSync 因 hasLyrics == false 早退（lock_screen_lyrics_service.dart:146-149）
    → 原生 MusicService.hasLyrics 保持 false
      → 通知栏第二行回落歌手名（MusicService.kt:749-753）
      → DISPLAY_SUBTITLE 条件写入不生效（MusicService.kt:590-592）→ 车机副标题也就没有歌词
```

**两个附带发现（同期修复）**：

**(a) 车机链不读本地缓存** —— 兜底结果会 `saveLyrics` 写缓存（`:386` / `:444`），UI 下次秒出；车机链从不读缓存 ⇒ **同一首歌第二次播放，UI 有歌词、车机依然没有**。最容易被忽略、也最容易自证的一条。

**(b) `structuredLyrics` 两套互不兼容的解析器**：

| 解析位置 | 读取字段 |
|---|---|
| 车机链 `_convertStructuredToLrc`（`:2521-2538`） | `line['text']` + `line['startTicks']`（Jellyfin 形状） |
| 三个 UI 入口（`synced_lyrics_view.dart:333-336` / `car_mode_screen.dart:146-149` / `compact_lyrics_view.dart:137-140`） | `line['value']` + `line['start']`（Subsonic 形状） |

同一份响应，两条路径**必有一条解析出空行** → 0 行 → 该入口无歌词。§4 方案 C 的「双键」只解决了**道理鱼这一条源**的形状，没有消除两套解析器并存 —— 归一化必须在 P0 一并收敛（§5.3 / §5.4 第 13 项）。

> **10 秒判别法（不依赖车机）**：看**手机通知栏第二行** ——
> 滚歌词 ⇒ 车机链有歌词，车机不显示则属「车机读法」问题（`docs/车机媒体会话与歌词推送技术方案.md` §4.4）；
> 显示歌手名 ⇒ 车机链没拿到歌词，即本节问题。

## 3. 不变量（修复不得破坏）

1. **车机副标题 / 通知栏 / 锁屏歌词不可退化**（2026-10-08 修订）—— 原表述是「本次**不得改动其输入形态**」，现修订为「**不得退化 + 不得与 UI 不一致**」：
   - 有歌词时必须仍有（2026-09-23 验收的能力不得被削弱，见 `docs/车机媒体会话与歌词推送技术方案.md`）；
   - 取源链与**来源优先级**必须与 App 内入口一致（「服务器 / 缓存 / 兜底」的关系只允许定义一次）；
   - 推送链路（`LyricsPlugin` / `MusicService`）本身仍然**一行不动**。
2. **离线可用** —— 已下载歌曲在无网时歌词仍要能显示 → 缓存优先**不可**改成「服务器优先」。
3. **Navidrome / Jellyfin 的服务器歌词路径零影响**（2026-10-08 修订）—— 改动限制在 `isDaoliyu` 分支、缓存读取判定、以及**车机链新增的兜底与形状归一化**内；兜底行为对齐 UI 侧（缓存优先、命中后写缓存），不改变服务器歌词本身的解析结果。
4. **歌词不阻塞播放** —— 现有 try/catch 语义保持。
5. **单一取源语义**（2026-10-08 新增）—— 「先查哪一级、缓存怎么判定、兜底何时介入、形状怎么归一化」只允许存在**一份**实现（§5.3 的 helper），禁止在入口内复制。

## 4. 方案选型

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A 消费端各加分支 | 三个 UI 各加 `syncedData['lyrics'] is String → SyncedLyrics.fromLrc()` | 改动最小 | 3 处重复；契约仍是双形态，将来新增入口必再踩；缓存里的 `{'lyrics':...}` 也要每处记得处理 | 备选 |
| B 服务层改回 structuredLyrics | `_getDaoliyuLyrics` 只返回 `structuredLyrics`，并让 `_convertStructuredToLrc` 兼容 `{start,value}` | 契约统一，一处生效 | **动到车机那条链的转换函数**（须与 Jellyfin 的 `{startTicks,text}` 分支并存）；且「原始 LRC → 行数组 → 再转回 LRC」存在丢行/精度风险，回归面覆盖刚验收的能力 | 不采用 |
| **C 服务层返回双键（采用）** | `_getDaoliyuLyrics` 同时返回 `{'lyrics': <原始 LRC>, 'structuredLyrics': [...]}` | 单一改动点；两条链各自命中自己认的键；**车机链零改动**；`lyrics` 保留原始 LRC 无损 | 数据冗余（同一份歌词两种形态，KB 级）；契约是**过渡形态** | ⭐ 采用 |

**采用 C 的核心理由**：本次问题的本质是「服务层输出形态与消费者不匹配」，而两个消费者的需求天然不同（一个要无损 LRC 喂时间轴解析器，一个要行数组做逐行渲染）。双键让**两个需求都就地满足**，把回归面压到最小，代价只是 KB 级冗余。

### 4.1 车机链取源统一（2026-10-08 二次增补，采用）

§2.6 的修法**不引入新方案**：让车机链**复用 §5.3 的同一个 helper**（缓存判定 + 取源链 + 形状归一化），即把「所有入口共用一套取源语义」从 P1 目标**提前到 P0 范围内**（用户 2026-10-08 拍板，见 §8 决策 5）。

| 备选 | 结论 |
|---|---|
| 车机链**就地复制**一份「读缓存 + 兜底」逻辑 | ❌ 不采用：把 4 处重复变成 5 处，§2.6(b) 的形状问题也会被复制一遍 |
| 完整抽取 `LyricsRepository` 并迁移 4 个 UI 入口 | ⏸ 仍留 P1（§8.1）：P0 只做「helper + 车机链接入」这一最小闭环，控制回归面 |
| **复用 helper 接入车机链（采用）** | ⭐ 一处实现、两条链共享，同时消除 §2.6(a)(b) |

## 5. 设计

### 5.1 数据契约（`getLyricsBySongId()`，`isDaoliyu` 且自研接口拿到有效 LRC 时）

```dart
{
  'lyrics': '<原始 LRC 文本>',        // 无损：供 player_provider / LyricsManager 直接解析时间轴
  'structuredLyrics': [              // 行级视图：供三个 UI 入口逐行渲染
    {'synced': true, 'line': [{'start': <ms>, 'value': '<text>'}, ...]},
  ],
}
```

- `structuredLyrics` **仅在 LRC 含有效时间轴行时产出**；纯文本（无 `[mm:ss.xx]`）时只返回 `lyrics` —— 与现状一致（此时两侧都拿不到有效歌词，仍走兜底）。
- 双语交错行（同时间戳原文 + 译文）**原样保留两行**，与现有 `SyncedLyrics.fromLrc` 行为一致。
- 自研接口失败 / 无有效歌词 → 返回 `null`（保持现有降级语义，不抛给 UI）。
- 其余形态（`{'value': ...}` 纯文本、Jellyfin `structuredLyrics`）语义不变。

### 5.2 LRC → 行数组的解析（避免第三份重复实现）

`lrclib_service.dart:112-154` 与 `netease_lyrics_service.dart:186-227` 已各有一份**完全等价**的私有实现（正则 + 毫秒归一化 + `text.isEmpty` 过滤）。本次：

- 新增公共纯函数 `lrcToStructuredLines(String lrc)`（建议落 `lib/services/lyrics/lrc_parser.dart`）；
- **P0 只新增函数并供道理鱼分支调用**（不动 LRCLIB / 网易云，控制回归面）；
- **P1** 再把那两处私有实现替换为该公共函数（等价重构，需回归）。

### 5.3 缓存来源标记 + 会话级复查（解决 §2.4 的永久占位）

缓存文件**顶层**新增两个键（对旧代码无害：旧代码只读 `lyricsList` / `lyrics`，未知键被忽略）：

```json
{ "lyricsList": {...}, "lyrics": {...}, "v": 2, "source": "daoliyu|server|lrclib|netease" }
```

加载判定（**所有入口**共用同一 helper —— 4 个 UI 入口 + 车机链 `_loadAndSyncLyrics`，2026-10-08 二次增补）：

```
cached = getLocalLyrics(songId)

if (cached != null && cached.source ∈ {daoliyu, server})
    → 直接用（现状不变，零网络）

if (cached != null && (cached.source 是兜底来源 || 无 v/source))
    if (!sessionRechecked.contains(songId))          // 每进程每首最多复查一次
        sessionRechecked.add(songId)
        server = await getLyricsBySongId(songId)
        if (server != null) { 覆盖缓存(source=daoliyu/server); 返回 }
    → 用缓存的兜底结果

// 无缓存
→ 服务器 → LRCLIB → 网易云（现有链），命中后写缓存并带 source
```

要点：

- **服务器查询返回 null 时不删除缓存** → 「离线」与「服务器确实无歌词」两种情形都安全退回缓存，**无需区分网络错误与空结果**（这是本设计能保持简单的原因）。
- **会话级 Set 而非 TTL**：每次启动 App 后，每首「被兜底占位」的歌**最多多一次**服务器查询，之后回到零请求；用户在道理鱼里补了歌词 → **重启 App 即生效**，不需要清缓存、也不需要等 TTL。
- **存量缓存迁移零成本**：旧文件无 `v`/`source` → 视为「来源可疑」→ 走第二条分支被自动复查纠正；**不清空任何缓存**（离线下载的歌词不受影响）。
- **新增：服务器歌词命中后也写缓存**（`source: 'daoliyu'`）。现状是 UI 拿到服务器歌词**不写缓存**，导致离线时看不到、且每次都要重新请求。

### 5.5 纯文本（无时间轴）歌词策略 —— **已拍板：选项 A**（2026-10-08）

`LyricsManager.parse`（`lyrics_manager.dart:48-91`）只认 `[mm:ss.xx]` 行。§5.3 的统一取源链会把「纯文本歌词」也带进车机链（现状：UI 侧用 `SyncedLyrics.fromPlainText` 能显示，车机链永远拿不到）。

| 选项 | 做法 | 车机/通知栏表现 | 结论 |
|---|---|---|---|
| **A** | 合成"一行 LRC"：把纯文本首行包装成 `[00:00.00]<首行>` 后走现有链路 | 副标题**静态**显示首行，不滚动 | ⭐ **采用**（用户 2026-10-08 拍板） |
| B | 纯文本不进车机链（保持现状） | 回落歌手名 | 备选：最安全，但该类歌在车机上永远没歌词 |
| C | 按行均分到歌曲时长，伪造时间轴 | 会"滚动"但与音乐不同步 | 已否决：错位比静态更糟 |

**精确规则（P0 实现口径）**：

1. **触发**：取源链拿到的歌词 `isLrc == false`（整段不含任何 `[mm:ss.xx]` 时间轴行）。
2. **选行**：按行拆分 → 去掉空行 → 去掉**元信息行**（`作词|作曲|编曲|制作人|演唱|歌手|词|曲|OP|SP|混音|母带|录音|出品|监制` 等前缀 + `:`/`：`）→ 取剩下的**第一行**。
   - 该过滤是必要的：纯文本歌词首行极常见是「作词 : XXX」，直接取首行会让车机显示「作词 : XXX」这种非歌词内容。
3. **包装**：产出单行 LRC `[00:00.00]<该行>`，走现有 `loadLyrics` + `startSync` 链路。
4. **效果**：`LyricsManager.parse` 得 1 行（`timestamp = 0`），`getCurrentLine(position)` 对任意 `position >= 0` 都返回该行（`_findLineIndex` 取「最后一个 `timestamp <= position`」，`lyrics_manager.dart:147-180`）⇒ 通知栏 / 车机副标题**静态**显示首行。
5. **退化**：若过滤后无可选行（纯文本全是元信息/空行）→ 退化为**选项 B**（不推，回落歌手名）。
6. **不截断**：超长行交由系统省略号处理，不引入长度魔法（少一个可调参数）。

> 与 §5.1 的关系：§5.1 已明确「纯文本（无 `[mm:ss.xx]`）时只返回 `lyrics`，此时两侧都拿不到有效歌词，仍走兜底」—— 选项 A 是在**消费端**对该描述做的增强，**服务层契约不变**。
> UI 侧不受影响：三个 UI 入口继续用 `SyncedLyrics.fromPlainText` 全量展示纯文本歌词。

## 7. 测试与验收

**单测**

1. `lrcToStructuredLines`：标准 LRC / 3 位毫秒 / 双语同时间戳两行 / 无时间轴 / 空串 / 含 `[ti:]` 等元数据行。
2. `_getDaoliyuLyrics`（mock `_apiGet`）：有效 LRC → **同时**含 `lyrics` 与 `structuredLyrics`；无时间轴 → 只含 `lyrics`；`candidates` 空 → null；结构异常 → null。
3. `lyrics_cache`：服务器来源缓存 → 不复查；兜底来源 / 无 `source` → 首次复查；同会话第二次 → 不复查；复查拿不到服务器歌词 → **仍返回缓存且不删**。
4. 回归：`synced_lyrics_view` / `car_mode_screen` 的 `structuredLyrics` 命中路径行为不变。
5. **取源链（`lyrics_source`，2026-10-08 二次增补）**：缓存命中 → 不再发网络请求；服务器命中 → `source=server`；服务器全无 + 网易云开 → `source=netease` 且写缓存；两开关都关 → `null`；两种 `structuredLyrics` 形状归一化后都能产出合法 LRC（回归 §2.6b）；纯文本 → 断言产出单行 `[00:00.00]<首行>`、元信息行被过滤、过滤后为空则退化为不推（§5.5 选项 A）。

**真机验收（用户）**

1. 播一首**从未播放过**的有歌词的歌 → 全屏歌词页显示道理鱼的**中英双语**，与道理鱼 WebUI 一致。
2. 播一首**之前歌词不对**的歌 → **重启 App** 后播放 → 歌词被纠正为道理鱼版本（验证存量缓存迁移）。
3. 通知栏副标题 / 车机副标题仍随歌词滚动（**回归红线**）。
4. 导出日志（设置 → 关于 → 诊断）搜 `lyrics.load`（`event_types.dart:64`，**仅 LRCLIB/网易云打点**）→ 服务器有歌词的歌**不应再出现** `found: true`。
5. 断网播放已下载的歌 → 歌词仍可用（回归）。
6. 切一首道理鱼**确实没有歌词**的歌 → 仍能回退到 LRCLIB / 网易云（退化路径未被切断）。
7. **（§2.6 专项）挑一首「服务器没有歌词、App 内靠兜底显示」的歌**（诊断页 `lyrics.load` 的 `source` 为 `netease`）→ **手机通知栏第二行随歌词滚动** —— 这是「车机链已拿到歌词」的唯一判据。
8. **（§2.6a 专项）同一首歌暂停再播**（第二次播放，走缓存）→ 通知栏**仍应有歌词**。
9. **（§2.6 终点）车机媒体卡片第二行是否显示歌词** —— 若通知栏有歌词、车机没有，则属「车机读法」问题，转 `docs/车机媒体会话与歌词推送技术方案.md` §4.4，不在本方案范围。
