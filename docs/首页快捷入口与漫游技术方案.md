# 首页快捷入口（歌单 / 收藏 / 漫游）与漫游播放技术方案

> 状态：**已实施**（2026-10-08；`flutter analyze lib/ test/` 0 error，`flutter test` **204 通过 / 5 跳过**；**尚未真机验收、未提交**）
> 起因：用户 2026-10-08 提出——「为你制作没什么用」，改成「歌单 / 收藏 / 漫游」入口；「最近播放」里不要再插歌单和收藏；新增「漫游」= 全曲库随机 + 无限续播，一键进入（对标飞牛音乐）。

---

## 1. 背景

三件事合并成一轮改造：

1. **砍掉「为你制作」**（通勤活力 / 专注学习 / 睡前放松 / 你的最爱 4 张 Mix 卡）。
2. **首页新增「漫游」入口**，行为 = 点一下立刻开始全曲库随机播放，且**播不完**（自动续播）。
3. **处理「封面显示不全」**：首页「你的歌单」里的服务器收藏歌单（截图里的 `cheng喜欢的音乐` / `sellen喜欢的音乐`）封面看着不完整。两处一起解决：① 「最近播放」的 2×2 拼图卡直接删掉（§7）② 「你的歌单」的卡片换成流体卡，不再显示封面（§8.6）。

关于第 3 点的根因（已定位，非猜测）：

- 该卡是 `lib/screens/home_v2_screen.dart:642-686` 的 `_PlaylistCardV2`，封面走 `AlbumArtwork(coverArt: playlist.coverArt, size: 150, borderRadius: 8)`。
- `AlbumArtwork` 对网络图用 **`BoxFit.cover` 强制裁成 1:1**（`lib/widgets/album_artwork.dart:243`）。道理鱼给歌单的封面不是 1:1，于是两边被裁 → 「显示不全」。
- 另有一处同类观感问题：首页「最近播放」里的歌单/收藏卡 `_CollectionCardV2` → `CoverCollage` 2×2 拼图（`lib/widgets/mix_grid_section.dart:258-300`），**封面不足 4 张时剩余格子是透明的**（`_cell` 里 `index >= coverArts.length` 直接返回透明 `ColoredBox`，见 `mix_grid_section.dart:294-299`）。

**关键推论**：改成「为你制作那种流动卡」（`MixCardData(useFluidGradient: true)` → `FluidBackground`，`lib/widgets/mix_grid_section.dart:177-193`）后，**卡片根本不显示封面**——它是拿封面颜色生成流沙流体场。所以「封面显示不全」不是被修好，而是**不再存在**。这是本方案选择流体卡的主要理由。

## 4. 新小节：歌单 / 收藏 / 漫游

### 4.1 组件

复用 `MixGridSection`（标题 + `GridView`，内部 `FluidBackgroundScope` 让本段所有卡**共用一个 Ticker**——`mix_grid_section.dart:109`，这条别破坏）。

```dart
MixGridSection(
  // 不设小节标题（见 §8.7）
  hPad: hPad,
  columns: 3,                        // 固定 3 列一行（移动 / 桌面一致）
  childAspectRatio: 0.70,            // 3 列专用，见下方警告
  cards: [
    // 歌单：卡面 = 最近播放的那个歌单（§4.5）
    MixCardData(title: <歌单名 / 「歌单」>, subtitle: <「N 首」/「全部歌单」>,
                imageUrl: <该歌单封面>, useFluidGradient: true,
                onTap: → PlaylistScreen(最近那个) 或 PlaylistsScreen(回落)),
    MixCardData(title: l10n.favorites, subtitle: <「N 首」>,
                imageUrl: <第一首收藏的封面>, useFluidGradient: true,
                onTap: → FavoritesScreen),
    MixCardData(title: l10n.roaming, subtitle: <「随机漫游曲库」>,
                imageUrl: null, useFluidGradient: true,
                onTap: → startRoaming()),
  ],
)
```

**⚠️ 3 列必须同时改 `childAspectRatio`（否则必 overflow）**：`MixGridSection` 现在的比值是按列数硬编码的（`mix_grid_section.dart:129`：2 列用 0.74、其余用 0.9）。3 列时单卡宽约 101dp（360dp 屏 − 32 左右边距 − 24 列间距），而卡内高度 = 封面 101 + 8 + 标题(~18) + 2 + 副标题(~16) ≈ 145 → 需要比值 ≈ **0.70**。沿用 0.9 会直接 RenderFlex overflow（`_MixCard` 是 `Column`，`mix_grid_section.dart:206-230`）。
做法：给 `MixGridSection` 加可选 `childAspectRatio` 参数，**不改默认值**，避免波及别处。

> ⚠️ **已修订（2026-10-08 第二轮，见 §12.3）**：三张卡改为**横向滑动 + 固定 150dp 宽**后
> 不再有 GridView，`childAspectRatio` 随之作废（改由固定宽高决定）。上面的推导保留，作为当时的依据。

### 4.2 取色源

`FluidBackground` 的取色源就是 `MixCardData.imageUrl`（封面 URL），取不到则包内回落默认深色 mesh（`mix_grid_section.dart:182-193`）。

- **歌单**：**最近播放的那个歌单**（见 §4.5）的封面 —— `playlist.coverArt`，为空则取该歌单第一首歌的封面。
- **收藏**：`libraryProvider.starred` 第一首的封面；无收藏则 null。
- **漫游**：**没有天然封面**。已拍板：**每次回到首页随机换一组配色**（+ 随机 seed），从一份**手工挑选的调色板池**里抽，而不是从图里提取——因为要保证「好看」。实现见 §4.6。

### 4.3 点击行为

| 卡 | 行为 |
|---|---|
| 歌单 | 有最近记录 → `PlaylistScreen(playlistId: …, playlistName: …)`（直进那个歌单）；无记录 → `PlaylistsScreen`（所有歌单） |
| 收藏 | `NavigationHelper.push(context, const FavoritesScreen())` |
| 漫游 | `startRoaming()`（见 §5） |

### 4.4 空态

三张卡**不因数据为空而隐藏**（它们是入口，不是内容）。仅当未登录 / 未初始化时整节隐藏。副标题用 `MixCardData.subtitle`，现有组件已支持（`mix_grid_section.dart:222-227`）：

- 歌单：有最近记录 → 主标题 = 歌单名、副标题 =「N 首」；无记录 → 主标题 =「歌单」、副标题 =「全部歌单」。
- 收藏：主标题 =「收藏」、副标题 =「N 首」。
- 漫游：主标题 =「漫游」、副标题 = 固定文案（如「随机漫游曲库」）。

### 4.5 「歌单」item 承载「最近播放的歌单」（2026-10-08 决定）

原「最近播放」混合区里的歌单卡被砍掉（§7），但它背后的数据源 `PlaybackContextTracker` **不废弃**——语义整体搬到新小节的「歌单」item 上：

```dart
// tracker.items 最新在前（record() 里 insert(0)），第一条即最近播放的歌单。
final recentPlaylist = tracker.items
    .where((e) => e.kind == 'playlist')
    .firstOrNull;   // package:collection 的 IterableExtension，仓库已在用
```

- 有记录 → 卡面 = 该歌单（名字 + 封面取色），点击直进该歌单。
- 无记录 → 卡面回落为「歌单 / 全部歌单」，点击进 `PlaylistsScreen`。
- ⚠️ tracker 里还有 `kind='starred'` 的记录（收藏）。**本方案不使用它**——「收藏」item 是固定入口，不随最近播放变化；记录侧照旧写入，不删。

数据流：`PlaylistScreen._playAll()`（`playlist_screen.dart:75`）仍是唯一的 `kind='playlist'` 写入点，**这条不变**；变的只是消费方——从「最近播放」换成新小节的「歌单」item。

### 4.6 漫游卡的随机配色（2026-10-08 决定）

要求：**每次回到首页换一组颜色，但必须好看**。

关键前提：`FluidBackground` 支持直接传 `colors`（4 个固定颜色，**跳过取色**，优先级高于图片源）——见 `packages/fluid_mesh_background/lib/src/fluid_background.dart:69-70`。所以不必造图，也不用依赖封面。

做法：

1. 在 app 侧定义一份**手工挑选的调色板池**（约 8 组，每组 4 色）。配比照包内 `FluidPalette._select` 的思路：**2 个高饱和 + 2 个深色**（`fluid_palette.dart:92-124`），既有色彩识别度又不糊成一片。
   ⚠️ **不要用 `FluidPalette.defaultColors`**（`fluid_palette.dart:26-31`）——那是一组深蓝紫，跟旁边两张彩色卡并排会显得「就它是灰的」。
2. 漫游卡用 `FluidBackground(colors: picked, seed: <random>)`。**seed 也要一起随机**，否则每次只是换色、流动纹样不变。
3. **触发时机 = 每次回到首页**。难点：首页在 `IndexedStack` 里，切 tab **不会重建**（`main_screen.dart:532-543`），没有天然的「回到首页」回调。
   - 方案：给 `NavigationHelper` 加一个**可多播**的 `ValueNotifier<int> tabIndex`，首页订阅它、值变 0 时换一组配色。
   - ⚠️ **不能复用现有的 `registerTabChangeCallback`**——它是**单槽**（`navigation_helper.dart:60-64`），已被 `main_screen` 占用，再注册会**直接打断切 tab**。
   - ⚠️ 桌面端切 tab 走的是 `main_screen.dart:368-372` 的 `onDestinationSelected`（直接 `setState`，**没走** `switchToTab`），要一并补上通知，否则桌面端不换色。
4. 状态放 `HomeV2Screen` 的 State（`_roamingPalette` / `_roamingSeed`），`setState` 重绘即可。**不持久化**——「回到首页就换」本来就是易失行为。

## 5. 漫游播放机制

### 5.1 起播（点一下立刻出声）

```
1. 池子 = libraryProvider.cachedAllSongs（本地全量，SQLite 已缓存）
   池子为空 → 回退 libraryProvider.randomSongs（服务端随机 50）
2. shuffled = [...pool]..shuffle()
3. 队列 = shuffled.take(ROAM_SEED_COUNT)   // 建议 100，见下
4. playerProvider.playSong(queue.first, playlist: queue, startIndex: 0)
5. 开启续播 = 打开 AutoDJ（`AutoDjMode` 置为 `shuffleLibrary`，或「路 3」下用户选定的续播方式），
   并把本地池交给 AutoDjService（见 5.2 / 5.3）
```

**为什么队列只塞 100 首而不是全库**：队列会被 `PlayerProvider` 持久化（`_keyQueue`，`player_provider.dart:296-376`），且 gapless 下要重建拼接音源；3200 首的队列在冷启动恢复与拼接源构建上都吃不消。100 首足够撑 5~6 小时，续播会接上。

### 5.2 续播（播不完）

现有 `AutoDjService.shuffleLibrary` 就是这套机制（`auto_dj_service.dart:160,194`）：队列剩余 ≤ 阈值（默认 2 首）时抽歌补队列，`_filterAndLimit`（`:322-338`）已做「排掉队列内 + 排掉最近加过的（`_recentlyAddedIds`，上限 100）」去重。

**但它现在的取歌源是 `getRandomSongs(size: songsToAdd*2)`——服务端随机**（`auto_dj_service.dart:195`），池子会从「本地全库」退化成「服务端随机若干首」。

**已拍板：走方案 B（本地全库乱序）。** 两个选择的对比留档：

- **方案 A（最小改动，未采纳）**：续播就吃服务端随机。改动≈0，但「全曲库漫游」名不副实，长听会明显重复。
- **方案 B（✅ 已选）**：给 `AutoDjService` 增加「本地池」来源——漫游时把 `cachedAllSongs` 的乱序副本交给它，续播从副本里顺序取；副本耗尽后重洗（并保留 `_recentlyAddedIds` 去重）。真正做到一轮内不重复、覆盖全库。改动集中在 `auto_dj_service.dart` 一个文件 + 调用方传参。
  - 实现要点：`AutoDjService` 新增 `setLocalPool(List<Song>?)` 与内部游标 `_poolCursor`；`_getShuffledLibrarySongs`（`auto_dj_service.dart:194-197`）改为「有本地池走池子，无池回落 `getRandomSongs`」，保证非漫游路径（设置里的其他模式）行为不变。
  - 池子耗尽判定：游标走到末尾 → 重洗并清空 `_recentlyAddedIds` 中已重洗的 id，避免误判为「重复」而空手。

### 5.3 与 AutoDJ 合并（已拍板方向）

**已定：漫游与 AutoDJ 合并成一个功能。** 理由是 AutoDJ 目前**只有设置页里一个被动的模式选择器**（`settings_playback_tab.dart:69-78`），全 app 没有任何「进入 AutoDJ」的入口——它必须等用户先手动播点什么才生效。漫游卡就是这个入口。

合并后的共同点：

- 两者本来就是**同一套机制**：`AutoDjService` 在队列快播完时补歌（`auto_dj_service.dart:140-197`），`PlayerProvider._addAutoDjSongs` 负责接入（`player_provider.dart:3145-3175`）。
- 因此**不再需要 `_roaming` 这种并行标志**——点漫游 = 「开启 AutoDJ 并立刻起播」，`AutoDjMode` 是唯一状态源。（本文档早先的「方案甲 / 方案乙」之争作废。）

**待拍板的是另外 5 种模式的去留**（`AutoDjMode` 现有 6 个值，`auto_dj_service.dart:9-16`）：

- **路 1（最保守）**：设置页的「自动播放模式」选择器**保留**；漫游卡 = 一键开启 + 起播，续播方式沿用当前模式（默认「随机播放曲库」）。代价：卡叫「漫游」，但续播可能是「相同艺术家」，语义拧。
- **路 2（真正合成一个）**：**只保留 `shuffleLibrary`**，删掉 `similarSongs` / `sameGenre` / `sameArtist` / `smartMix` 与设置页的模式选择器。连带可清理 `generateQueue` / `_calculateTransitionScore`（`auto_dj_service.dart:517-614`）与 `BpmAnalyzerService` 接入（`:417-467`）。**这是破坏性改动**，需确认这几个模式确实没在用。
- **路 3（折中）**：模式选择**从设置页搬进漫游**（长按漫游卡 → 单选 Sheet 选续播方式），设置页不再有 AutoDJ 小节。语义统一在「漫游」之下，功能一个不丢。

**✅ 已拍板：路 3** —— 模式选择搬进漫游（长按漫游卡 → 单选 Sheet），设置页的「自动播放」小节（`settings_playback_tab.dart:69-78`）整体移除；「每次追加数量」滑杆一并搬进漫游的选择 Sheet。

### 5.4 退出漫游

**合并之后这里有个必须想清楚的连带效应**：`AutoDjMode` 是全局单值（`auto_dj_service.dart:69`，持久化在 `_modeKey`）。所以「点过一次漫游」= 此后**任何**播放（手动点的歌单、专辑、每日推荐）都会在队列快播完时自动续歌——因为续播开关是全局的，不是绑在漫游队列上的。

**✅ 已拍板：不设退出** —— 接受上面的连带效应（用户点了漫游就是要「以后都自动播」）。备选方案留档：

- ~~显式关闭~~：漫游卡做成开关态（再点一次 = 关闭续播），或播放页给一个「漫游中」标记 + 关闭入口。
- ~~只在漫游队列内生效~~：需要给队列打来源标记，续播时校验——即回到被否掉的 `_roaming` 方案，与「合并」冲突。

以下情况无论如何都应关闭漫游：切到电台 / 有声书（这两条路径本来就不走 AutoDJ）。

### 7.3 附：「最近播放」现在的插入逻辑（回答 2026-10-08 提问）

`_buildRecentlyPlayed`（`home_v2_screen.dart:440-487`）的 `children` 是**按顺序拼接**的：

1. 先 `tracker.items.take(6)` —— `PlaybackContextTracker` 里的**歌单 / 收藏**
2. 再 `libraryProvider.recentAlbums.take(10)` —— 专辑

写入侧（`playback_context_tracker.dart:78-105`）：先按 `(kind, id)` 去重删除，再 `insert(0, …)` 置顶，上限 10 条，落 SharedPreferences（key `recently_played_collections`）。

- `PlaylistScreen._playAll()`（`playlist_screen.dart:64-76`）→ `kind='playlist'`、`name`=歌单名。**只在点「播放全部」时记录**，点单曲播放不记录。

## 8. 影响面与风险

### 8.1 l10n（本轮最大机械成本）

需**新增** `roaming`（漫游）**一个** key —— 小节不设标题，所以不需要 `quickEntries`（见 §8.7）。仓库有 **30 个 locale** 文件（`lib/l10n/app_localizations_*.dart`），需在 `app_en.arb` / `app_zh.arb` 加条目后跑 `flutter gen-l10n` 重新生成。

复用已有 key（无需新增）：`playlist`（歌单，`app_zh.arb:744`）、`favorites`（收藏，`:297`）、`yourPlaylists`（你的歌单，`:48`）。

### 8.2 流体卡数量变化（性能）

原「为你制作」是 4 张流体卡共 1 个 `FluidBackgroundScope`；新小节 3 张卡同样共 1 个 Scope → **Ticker 数不变（仍是 1）**，渲染压力略降。诊断埋点 `mixCardFluidBackground` 的 `cards` 值会从 4 变 3（`mix_grid_section.dart:86-101`）。

### 8.3 桌面端列数

桌面原本 `columns = 4`（`home_v2_screen.dart:80`）。新小节**固定 3 列**，桌面同样 3 列（3 张卡一行铺满，不出现 3+1 空位）；其余小节（探索发现等）仍沿用 `columns`。

### 8.4 漫游卡配色

无封面 → 默认深色 mesh，可能与相邻两张彩色流体卡不协调（§4.2）。需设计确认。

### 8.5 队列与 AutoDJ 的耦合

`PlayerProvider._addAutoDjSongs`（`player_provider.dart:3145-3175`）在 `_onSongComplete`（`:3026`）与 `skipToIndex`（`:3677`）两条路径触发。合并后**没有 `_roaming` 标志**，判定统一走 `AutoDjService.isEnabled`（`auto_dj_service.dart:92`）→ 这两条路径天然一致，无需额外处理。

要留意的是**本地池的注入时机**：池子在点漫游时 `setLocalPool()`，此后一直有效（§5.4 不设退出）。所以池子需要在 `libraryProvider.cachedAllSongs` 变化时刷新，否则曲库全量同步完成后池子还是旧的空列表。

### 8.6 「你的歌单」卡片也换成流体卡（2026-10-08 决定）

你选了「也换成流体卡」。所以「你的歌单」横滑列表**保留列表结构**（仍列出所有歌单名），但每张卡的卡面从 `AlbumArtwork`（`BoxFit.cover` 裁切）换成 `FluidBackground`（取色源 = 该歌单封面）。封面裁切问题因此消失。

- 位置：`home_v2_screen.dart:496-516` 的 `_PlaylistCardV2`；卡面换成 `FluidBackground(imageProvider: CachedNetworkImageProvider(coverUrl), seed: FluidBackground.seedForIndex(index), borderRadius: 8)`，并照 `mix_grid_section.dart:177-193` 的写法复用 App 封面缓存（`coverCacheManager` + `coverArtCacheKeyFromUrl`）。
- 外层需包 `FluidBackgroundScope`（`HorizontalScrollSection` 不支持，要在 `_buildPlaylists` 里自行包一层），否则 N 张卡各起一个 Ticker。
- ⚠️ **性能风险（本轮最需要真机实测的一项）**：首页流体卡从原来的 4 张（「为你制作」）变成 **3 + N 张**（N = `playlists.take(10)`，最多 10）。`FluidBackgroundScope` 只共享**时钟**，不共享 GPU 绘制——每个 `FluidBackground` 仍是一次独立的片元着色器绘制。ListView 离屏项会被回收（超出 cacheExtent 即销毁），实际同时在跑估计 5~8 个。
  退路（掉帧时按序采用）：① 减少列表条数 ② 只给前 3~4 张流体、其余回落静态取色渐变 ③ 调慢 `FluidBackgroundStyle.speed`。

### 8.7 新小节不设标题（2026-10-08 决定）

> ⚠️ **已修订（2026-10-08 第二轮，见 §12.3）**：用户真机验收后反馈「没有标题感觉很奇怪」，

### 12.2 修复「收藏」恒为 0 / 取不到色（真因**不是**歌曲-专辑拆分）

**真因（已核实）**：`LibraryProvider._starred`（`library_provider.dart:77`，初始 `null`）
**只在 `loadStarred()` 里被赋值**，而 `loadStarred()` 的 4 个调用点全是**收藏/取消收藏动作**
（`library_provider.dart:1309,1322`、`player_provider.dart:3876,3892`）。
**冷启动链路 `initialize()`（`library_provider.dart:476-556`）里没有它** —— 它只加载
`loadRecentAlbums / loadRandomSongs / loadPlaylists / loadArtists`（`:524-528`）。

于是：`_starred == null` → 首页 `libraryProvider.starred?.songs ?? const []`（`home_v2_screen.dart:432`）
恒为空 → ① 副标题 `'${favorites.length}'` 恒为 **0** ② `_firstCoverUrl` 遍历空列表直接 `return null`
→ `FluidBackground` 取不到色 → 回落包内默认深蓝紫（`fluid_palette.dart:26-31`），
看起来就像"没获取到封面"。**只有用户在本会话里做过一次收藏/取消收藏，这两个症状才会消失。**

**修法（推荐）**：`initialize()` 里补一次 `await loadStarred()`（与 `loadPlaylists` / `loadArtists` 同批）。

- **为什么不用本地库计数**：`Song.starred` 确实落进了 SQLite（`library_database_service.dart:82,354,389`），
  `cachedAllSongs.where((s) => s.starred == true)` 能离线算出来，还省一个请求 —— 但那是**第二个数据源**，
  会和 `FavoritesScreen` 直读 `getStarred()`（`favorites_screen.dart:39`）打架，
  将来必然出现「首页 N 首 / 收藏页 M 首」。本轮取**单一数据源**（服务端 `getStarred2`），
  代价只是冷启动多 1 个轻请求。
- **不选「让首页自己拉一次」**：同上，会出现两个真相。
- ⚠️ 它是加进 `initialize()` 里那个 `Future.wait`（`library_provider.dart:524-537`）的，于是与另外
  4 个请求**共享 5s 超时预算**。`getStarred2` 只返回收藏条目、比那 4 个都轻，判断可接受；
  若真机上出现「Server initialization skipped」，把它挪到 `Future.wait` **之后**单独 `loadStarred()`
  （代价是计数晚一帧出现，会有 0 → N 的闪动）。
- ⚠️ `loadStarred()` 在 `_serverOfflineMode` 下会直接 return（`library_provider.dart:1176`）——
  离线时计数仍为 0，这是**预期行为**，不是本 bug。

**⚠️ 必须向用户说清的一点**：流体卡**不显示封面图**，`MixCardData.imageUrl` 只是**取色源**
（`mix_grid_section.dart:215-228`）。所以修好后「收藏」卡表现为**被第一首收藏的歌染上颜色**，
而不是卡上出现一张封面图。若你要的是"卡上真的显示封面"（Apple Music 那种），
那是**另一套卡面**（需要新决策），不在本轮。

### 13.2 取色：每次回到首页随机挑一首歌的封面

新增状态与逻辑（`home_v2_screen.dart`）：`_coverEpoch` / `_coverRandom` / `_coverSig` /
`_favoriteCover` / `_recentPlaylistCover` / `_playlistCovers`，由 `_rollCoversIfNeeded()` 统一重抽。

**池子（按语义优先，缺则回落）**

| 卡 | 主池子 | 回落 |
|---|---|---|
| 收藏 | 收藏歌曲的封面 | 全曲库 |
| 歌单（最近播放的） | **该歌单的歌**（`Playlist.songs`） | 全曲库 |
| 你的歌单（每张） | 该歌单的歌 | 全曲库 |

⚠️ **为什么要有「全曲库」回落**：本地**没有**「歌单 → 歌曲」的缓存 —— `Playlist.songs`
只有用户**打开过**那个歌单（`PlaylistScreen` → `getPlaylist(id)`）时才会被填充，SQLite 的
`playlists` 表也不存歌曲（`library_database_service.dart` 只有 songs/albums/artists/playlists
四张表，无 `playlist_songs`）。没有回落的话，「你的歌单」里 10 张卡基本都只能停在
`playlist.coverArt` 上、**等于没随机**。代价是：未打开过的歌单，卡面颜色与它本身无关。
> 若要「每张卡只用该歌单自己的歌」，得先加「歌单 → 歌曲」的本地缓存（或每次进首页拉 N 个
> 歌单详情）——那是另一个改动，本轮不做。

**触发时机 = 回到首页**：沿用 §4.6 已有的 `NavigationHelper.tabIndex` 信号
（`_onTabIndexChanged` 里 `_coverEpoch++`），与漫游换色同一个入口。

⚠️ **为什么是「签名 + 懒重抽」而不是在 `didChangeDependencies` 里抽一次**：
首页首帧时 `LibraryProvider` 还没初始化（池子为空），若那时抽完就不再抽，收藏卡会一直停在
默认深色 mesh —— 正是 §12.2 要修的「取不到色」。签名里带上池子规模与 `_coverEpoch`：
**数据加载完（签名变）或回到首页（epoch 变）都会重抽**，普通重建则不动（不会每帧换色）。
写法与同文件既有的 `_cachedFeed` / `_lastFeedKey` 一致。
